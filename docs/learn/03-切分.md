# 03 切分：第一步就容易踩坑

## 这篇解决什么问题

**切分是 RAG 里最容易被瞎调、也最容易调出假象的一步。**

很多人调 `chunk_size` 的方法是"试试 200，再试试 500，哪个分数高用哪个"。
这篇要说明：**分数高可能是假的。**

---

## 先跑一下

```bash
# 默认（90 字）
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt

# 换成 200 字
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt --chunk-size 200
```

对比两次报告里的两行：

1. `各切分方案切出的片段数`
2. `指标对比` 里"仅向量召回"那一行

**注意：片段变少了，指标变好了。** 记住这个反常的地方。

---

## 看到了什么

我用同一份语料（`examples/corpus`，4 篇文档）跑了一遍，只看向量召回：

| 切分窗口 | 片段数 | Recall@5 | MRR@5 | nDCG@5 |
|---|---|---|---|---|
| 60 字 | 21 | 0.900 | 0.608 | 0.679 |
| 90 字 | 14 | **1.000** | 0.688 | 0.765 |
| 120 字 | 10 | 1.000 | 0.713 | 0.760 |
| 200 字 | 7 | 1.000 | 0.838 | 0.857 |
| 300 字 | **4** | 1.000 | **0.854** | 0.891 |
| 500 字 | **4** | 1.000 | **0.854** | 0.891 |

三个现象：

1. **片段数一路降**（21 → 14 → 10 → 7 → 4 → 4）
2. **指标一路升**（MRR 0.608 → 0.854）
3. **300 和 500 完全一样**——数字一模一样

如果只看这张表，结论显然是"窗口调到 300 字，MRR 0.854 最好"。

**但这是错的。** 下面解释为什么。

---

## 为什么是这样

### 先说为什么必须切

不能把整篇文档直接塞给大模型吗？三个原因：

| 原因 | 说明 |
|---|---|
| **上下文有上限** | 每篇文档都塞进去，很快就超了 |
| **无关内容会干扰** | 一篇讲 5 个主题的文档里，只有 1 段相关。整篇塞进去，模型要自己从 5 段里挑 |
| **成本** | 输入越长越贵，而且慢 |

所以必须切。问题只是**在哪切**。

### 两种切法，各自的毛病

这个项目实现了两种：

**固定窗口**（`FixedWindowChunkingStrategy`）

```
按字数硬切：数到第 90 个字就断，不管断在句子中间还是词中间。
```

优点是长度一致、实现简单。缺点是**会把一句话切成两半**。

**递归字符**（`RecursiveCharacterChunkingStrategy`）

```
先按段落切。段落还是太长，再按句子切。句子还太长，才按字数硬切。
```

优点是尽量保证语义完整。缺点是长度不一。

### 关键：看一眼真实的片段

这是 `billing-rules.md` 的原文（关键那句我标出来了）：

```
# 计费规则说明

本产品采用按量计费模式，费用在每个自然月结束时结算。
账单会在次月 3 日前生成，可通过控制台的账单中心查看。      ← 答案在这
计费项包括三部分：计算资源、存储空间和网络流量。
...
```

两种切法切出来的第一个片段，**长度都是 90 字左右，但内容不一样**：

**递归字符切出来：**

```
# 计费规则说明

本产品采用按量计费模式，费用在每个自然月结束时结算。
账单会在次月 3 日前生成，可通过控制台的账单中心查看。
```

（到这里正好是段落边界，就断了。**只讲账单周期，很纯。**）

**固定窗口切出来：**

```
# 计费规则说明

本产品采用按量计费模式，费用在每个自然月结束时结算。
账单会在次月 3 日前生成，可通过控制台的账单中心查看。

计费项包括三部分：计算资源、存储空间和网络流量
```

（凑满 90 字才断，把下一段"计费项"也拽进来了。**混了两个话题。**）

**两个片段都包含答案。** 但固定窗口那个的向量，
是"账单周期"和"计费项"两个话题的平均值。

问"账单什么时候出"的时候，它**没有那么像**了——语义被稀释了。

> 这就是第 2 篇里那个 `—` 的真正原因。不是答案被切断了，
> 是含答案的片段被稀释，排名掉到 5 名之外。

### 再说那两个"作弊"机制

回头看那张表：为什么片段越大指标越好？有两个独立原因。

**机制一：片段数少到 topK 已经能覆盖全部**

看 300 字那行：**只有 4 个片段**，而 `topK` 默认是 5。

"取前 5 条"对一个只有 4 条的库，等于**把整个知识库都给了**。
Recall 必然 1.000——这不是检索准，这是没得选。

所以 300 和 500 完全一样：4 篇文档总共就两千多字，
切到 500 字也切不出第 5 个片段了。

**验证一下**：把 `topK` 压到 2，让"返回全部"这个便宜吃不到：

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt --top-k 2
```

结果（我实测的）：

| 切分窗口 | 片段数 | Recall@2 | MRR@2 |
|---|---|---|---|
| 90 字 | 14 | 0.800 | 0.625 |
| 200 字 | 7 | 0.800 | 0.813 |
| 300 字 | 4 | 0.900 | 0.813 |

Recall 从"人人都 1.000"变成有差别了。但**片段大还是占便宜**——这就是第二个机制。

**机制二：片段越大，越容易"沾到"答案**

一个片段装的内容越多，它包含答案的概率就越高。
但代价是：**这个片段里无关的内容也越多。**

模型拿到这个片段，得自己从 200 字里挑出相关的那 20 字。
片段越大，混进来的噪音越多。

**所以"片段大 → 指标好"是个陷阱**：指标只看"答案在不在前 K 条里"，
不看"这一条里有多少是废话"。

### 报告里那条提醒就是拦这个的

如果你把 `--chunk-size` 调大，报告会多出一条：

```
⚠ 但别急着下结论：片段切得越大，一个片段里装的内容越多，
命中率天然就越高——这不一定说明检索变好了。
还要看喂给模型的上下文里有多少是无关内容（片段越大越多），
以及总片段数是否少到「返回前 K 条」已经接近返回全部。
```

**两种作弊机制它都点了名。**

## 改一改试试

### 试 1：把 topK 压到 2，看假象消失

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt --top-k 2
```

对比默认 `topK=5` 时的 Recall。**片段大的那个优势会缩小。**

### 试 2：同一个窗口，换个切法

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt --chunk-size 90
```

报告里会同时出现"递归切分 90 字"和"固定窗口 90 字"。
**窗口一样、片段数也一样（都是 14），但指标不同。**

差别就来自"切在语义边界"和"凑够字数就断"。

### 试 3：切得特别碎

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt --chunk-size 40
```

实测结果：片段从 14 个涨到 **31 个**，Recall 从 1.000 掉到 **0.800**。

**这是另一种失败**：一段完整的话被切成几块，哪一块都不完整，
语义都缺一部分，于是谁都匹配得不够好。

---

## 小结

1. **切分必须在语义边界上。** 固定窗口保证长度一致，代价是切断句子、混进别的话题。
2. **片段越大，指标越好看，但那是假象。** 两个独立原因：片段数少到 topK 能覆盖全部；片段内容多更容易沾到答案。
3. **看指标时先看片段数**。片段数接近或少于 topK 时，Recall 没有参考价值。
4. **语义稀释**：一个片段里混两个话题，向量会变成两者的平均值，对哪个话题都不够像。
5. 切太碎也不行：一段完整的话被切散，谁都匹配不上。

---

## 常见误解

**"chunk_size 越大召回率越高，所以越大越好。"**

召回率确实会涨，但那是"给得多"不是"找得准"。
真正的代价是模型拿到更多无关内容，回答质量反而下降。
**这个工具只能量检索，量不了"回答质量"，所以别拿它的分数当唯一标准。**

**"固定窗口和递归切分差不多，随便选一个。"**

窗口一样、片段数一样，指标也可能不一样——因为片段的内容纯度不同。
上面 `billing-rules.md` 那个例子就是：同样 90 字，一个纯、一个杂。

**"我调 chunk_size 直到指标最好就行了。"**

如果只看这个工具的分数，你会一路往上调，最后调到"整个知识库只有 2 个片段"。
那时候检索已经不是检索了。

**记住一句话：这个工具告诉你"检索捞到了没有"，不告诉你"捞到的内容干不干净"。**
片段大小的取舍，最终要你自己权衡。
