# 06 评测集：怎么出题才有效

## 这篇解决什么问题

**指标算得再准，测试集出得不对，全是白搭。**

这篇讲怎么写测试集：expectation（期望文字）怎么写、负样本为什么必须有、
什么样的题能暴露问题。

---

## 先跑一下

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt
```

打开 `examples/eval.txt` 对照着看。文件不长，几十行。

---

## 看到了什么

测试集里每条用例长这样：

```
Q: 错误码 E4021 是什么意思
E: E4021 表示计费账户被冻结
```

- `Q:` 是用户会问的问题
- `E:` 是**期望被召回的片段里应该出现的一段文字**

还有一类只有 `Q:` 没有 `E:`：

```
Q: 如何申请退款
```

这叫**负样本**——"这个问题在知识库里本来就没有答案"。

---

## 为什么是这样

### 为什么 E 写"文字"而不是"片段编号"

最直接的想法是：直接写"答案在 `billing-rules.md` 的第 3 个片段"。

**不行。** 因为那个"第 3 个"取决于切分参数。

- 90 字切分时它可能是第 3 个
- 一旦你把 chunk_size 改成 200，它可能变成第 1 个
- 再改一次，它可能跨在两个片段中间

**编号一失效，所有指标都会变成 0。而你多半会以为是检索坏了**，
去查向量模型、去查索引，查半天。

写文字就没有这个问题：切分怎么变，只要那段文字还在某个片段里，就能找到。

### E 必须和原文**逐字**一致

这一点很容易踩。看这个真实例子：

语料里写的是：

```
当用量达到配额的 90% 时，系统会发送预警通知
```

测试集里写的是：

```
E: 90%时
```

**一个字都不差，就是少了个空格。** 结果：

```
诊断失败：测试集和语料对不上，请检查期望文字是否写错：
  - 用例「c002」有期望文字在语料里找不到：90%时
```

> 这个坑我自己踩过。仓库里 `examples/eval-format.txt` 那个"可用的例子"
> 就带着这个错，照着跑直接失败。现在已修正，并且加了测试盯着它。

**为什么不做"忽略空格"的宽松匹配？**

想过。但宽松匹配会带来新问题：如果工具帮你忽略了空格，
那它就也可能忽略了别的（全角半角、标点），
于是"这条 marker 到底对应哪句话"变得不确定。

**宁可报错，也不要静默地猜。** 报错你能改，猜错了你发现不了。

### E 写短一点，最好只写一小段

`E: 账单会在次月 3 日前生成` 这种长度还行。

但如果原文是一个跨三行的段落：

```
第一句话。第二句话。
第三句话。
```

你写成 `E: 第一句话。第二句话。第三句话。` 就匹配不上了——
因为原文中间有换行。

**规则：只写能唯一确定那个片段的一小段。** 越短越不容易对不上。

如果需要确认两个不同位置，写多条 `E:`：

```
Q: 存储满了会怎样
E: 达到配额的
E: 90% 时
```

一条用例可以有多个 `E:`，它们会被合并成"这个用例的期望片段集合"。

### 负样本为什么必须有

假设你的测试集里全是有答案的问题。

现在有个"作弊"的检索器：**不管问什么，都返回语料里最相似的那一条。**

在你的测试集上，它每次都能返回点什么，Recall 可能是 1.0——
因为每个问题确实都有答案，它恰好返回了最像的那条。

**你完全看不出它有问题。** 因为你的测试集从来没问过"这个问题答不出来"。

加上负样本之后，情况就变了：

```
Q: 手机客户端支持指纹登录吗      ← 语料里没有
Q: 如何申请退款                  ← 语料里没有
```

一个好的检索器在这些问题上应该**返回空或者低分**。
一个"总返回最相似"的检索器会给它们也返回一堆东西。

> **注意**：这个项目的三个指标（Recall/MRR/nDCG）都不直接惩罚负样本。
> Recall 给它们满分（没有该找的，就不存在漏找），
> MRR/nDCG 直接跳过（排序质量对它们无定义）。
>
> 所以负样本的作用是**让你看见**——明细表里那两行 `n/a` 提醒你：
> 还有这类问题存在。至于"应不应该返回结果"，得你自己判断。
>
> 这块业界还没有像 Recall/MRR 那样统一的口径，这个项目选择不发明新指标。

### 题目要覆盖不同类型的问法

`examples/eval.txt` 开头的注释说得很清楚：

```
# 这里刻意放了两类不同难度的问题：
#   - 精确编号类（错误码）：向量召回容易漏，关键词召回更有优势
#   - 同义改写类：问题用词和文档不完全一致，考验语义匹配
# 两类混在一起，诊断报告才有区分度。如果全是"和文档用词一样"的问题，
# 各种召回方式的表现会一模一样，报告也就给不出任何建议。
```

**这可能是整篇最重要的一句。**

如果你的测试集全是"用词和文档完全一样"的问题，那所有召回方式都会拿满分，
报告就变成"三种召回一样好，随便选"——这个结论对你毫无帮助，因为它是测试集造成的。

**测试集要有区分度，才能测出配置的区分度。**

常见的几类问法：

| 类型 | 例子 | 用来暴露什么 |
|---|---|---|
| 精确字符串 | `E4021 是什么意思` | 关键词召回强、向量召回的编号分辨力 |
| 同义改写 | `账单什么时候出`（文档写"生成"） | 语义匹配能力 |
| 长尾细节 | 某个具体数字、日期、限额 | 切分是否切断关键信息 |
| 多跳/组合 | 需要两段内容才能回答 | 单片段检索的局限 |
| 负样本 | 语料里压根没有 | 会不会硬凑 |

### 用例多少条合适

太少：噪声大。

这个项目的示例测试集有 10 条，其中一条没命中，Recall 就掉 0.1（10%）。
**一条用例的差别就抵得上 10% 的分数波动**，这种颗粒度做决策很危险。

太多：标注成本高，而且大部分用例不会带来新信息。

经验上：
- 起步 20～50 条，能看出大致趋势
- 要上线前，100 条以上，且覆盖上面那几类问法
- 每次线上发现"答错了"，就补一条用例进去

**最后这条最重要**：测试集是活的，不是写完就不管。
每次线上暴露一个问题，就沉淀成一条用例——这样测试集会越来越贴近真实。

## 改一改试试

### 试 1：故意写错一个 marker

打开 `examples/eval.txt`，把某条 `E:` 改一个字，然后重跑。

应该看到：

```
诊断失败：测试集和语料对不上，请检查期望文字是否写错：
  - 用例「c00X」有期望文字在语料里找不到：你写错的那个
```

**这个设计是刻意的**：宁可报错，也不静默跳过。
静默跳过的话，测试集会悄悄少一条用例，而你还在拿剩下的分数做决策。

### 试 2：删掉所有负样本

把最后两条只有 `Q:` 的用例去掉，重跑。

看报告里"（含 2 个负样本）"变成"（含 0 个负样本）"。

指标在这个例子里可能**看起来没变**——因为正样本本来就全命中，
Recall 不管分母里有没有负样本都是 1.000。
但**你现在失去了"检索器会不会硬凑"这个观察**。

这也说明一件事：**分数没变，不代表测试集没变**。
光看指标看不出测试集的质量问题。

### 试 3：只留同类问题

把"精确编号类"（c001～c003）全删掉，只留"同义改写类"，重跑。

看三种召回的指标差距会怎么变。**这是理解"测试集决定结论"最直接的办法。**

### 试 4：加一条你自己业务里的问法

```
Q: 你们的服务几点停机维护
E: 维护窗口
```

（前提是语料里真有这段。）重跑，看这条进没进前 5。

## 小结

1. **`E:` 写关键文字，不写片段编号。** 编号会随切分参数失效。
2. **必须和原文逐字一致，包括空格。** 对不上会直接报错，这是有意的。
3. **写短**。越长越容易因为换行、空格对不上。需要多处就写多条 `E:`。
4. **负样本必须有**，否则"永远返回最相似"的检索器也能拿高分。
5. **测试集要有区分度**，否则所有配置都是一样好，报告给不出任何建议。
6. **测试集是活的**。线上每暴露一个问题，就补一条。

## 常见误解

**"测试集随便标几条就行了，反正指标都是相对的。"**

不是。"相对"的前提是**测的东西有意义**。
如果测试集全是简单题，你的"最优配置"可能只是"最擅长做简单题的那个"。

**"标注太贵了，能不能让大模型自动生成？"**

可以辅助，但**必须人工复核**。
大模型生成的期望文字经常和原文字面不一致（就是上面那个空格的坑），
更麻烦的是它会生成"看起来对但实际不对"的用例。

**"我的测试集有 1000 条，肯定够了。"**

数量不等于质量。1000 条全是同一类问法，不如 100 条覆盖 5 类。

**"工具说某条用例对不上，我把它删了就行了。"**

先查清楚是 marker 写错了，还是**语料真的少了那段内容**。
如果是后者，那是个更严重的问题——你知识库里的东西丢了。
