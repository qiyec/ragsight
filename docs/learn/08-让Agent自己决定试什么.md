# 08 让 Agent 自己决定试什么

## 这篇解决什么问题

**调 RAG 的时候，组合是跑不完的。** 那怎么知道该试哪个？

标准做法是"挨个试"——但组合一多就不现实。这个项目的第二层就是让 Agent
自己决定下一步试什么，而不是把所有组合跑一遍。

这篇讲它怎么做到，以及**它为什么能成（也为什么不一定更省）**。

---

## 先跑一下

```bash
$env:DASHSCOPE_API_KEY = "你的key"
java -jar ragsight-agent/target/ragsight-agent-exec.jar diagnose
```

一次大约 15～20 秒，跑 7 步左右。

不想花 Key 的话，这篇的核心内容也能看懂——下面贴了真实运行的日志。

## 看到了什么

真实跑出来的（骨架，中间输出我省了）：

```
[调用] run_baseline(chunk_size=120)
       ↓ "基准结果（语料：示例：corpus，召回条数 5）：…"
[调用] compare_one_change(new_value=true, change=rerank)
       ↓ "只改了一处：重排 关 → 开…"
[调用] compare_one_change(new_value=90, change=chunk_size)
[调用] compare_one_change(new_value=200, change=chunk_size)
[调用] compare_one_change(new_value=300, change=chunk_size)
[调用] compare_one_change(new_value=60, change=chunk_size)
[调用] finish()
```

硬数据：

```
一共跑了 16 次实验，试过 11 个配置，用时 15.9 秒
最好的配置：递归切分 200 字 · 仅关键词召回
  Recall 1.000   MRR 0.938（基准 0.906）
```

**注意那个"只改了一处"。** 这是整套设计的关键，下面讲为什么。

---

## 为什么是这样

### 先说穷举为什么不行

这个项目能调的维度：

| 维度 | 可选值 |
|---|---|
| 切分策略 | 递归字符、固定窗口 |
| 切分窗口 | 60 / 90 / 120 / 200 / 300 / 500 …（连续取值，理论上无限） |
| 召回方式 | 仅向量、仅关键词、融合 |
| 要不要重排 | 开 / 关 |
| topK | 3 / 5 / 8 / 10 … |

光是"切分窗口固定 5 种取值"，全部组合就是：

```
5 种窗口 × 3 种召回 × 2 种重排 = 30 组
```

30 组，每组要跑完整个测试集。语料大一点、模型真调 API，这就不只是慢的问题了，
是钱的问题。

**而且大部分组合没必要试。** 如果召回率已经满分，问题肯定在排序，
那调切分窗口纯属浪费时间。

### 关键设计：一次只改一个

这是整个第二层的核心。对比两种工具设计：

**做法 A：开放"跑 N 种切分 × M 种召回"**

```java
@Tool("run_experiments")
String runExperiments(int chunkSize, String retriever, boolean rerank) { ... }
```

模型能做的，只是**把穷举换个方式跑一遍**。它还是得挨个试，只是不用你手敲命令了。

**做法 B：开放"把一个东西从 A 改成 B，看差别"**（这个项目用的）

```java
@Tool("compare_one_change")
String compareOneChange(String change, String newValue) { ... }
```

每次调用，**只改一个参数**，然后跑"改之前 vs 改之后"两组。

**为什么 B 更好：归因。**

如果一次同时改了切分和重排，指标变好了——是谁的功劳？不知道。
你只能换一种组合再试，这就是穷举。

如果一次只改切分，指标变好了——那就是切分的功劳。**这个结论可以直接拿去用。**

> 反过来说：**"一次只改一个"不是礼貌要求，是能否得出结论的前提。**
> 这也是为什么系统提示词里要把这条当成硬约束写死。

### 省了多少？诚实地说

先看这次实测：

- 自适应：**16 次实验**，试了 11 个配置
- 穷举：它探索了 5 种切分窗口，`5 × 3 × 2 = 30` 次

省了 14 次。

**但换个场景就不一定省了。** 我另一次跑的时候它停在"120 字"这一档没换窗口，
结果是 16 次实验，而"切分窗口固定 120 字"的穷举只要 `1 × 3 × 2 = 12` 次——
**那次它反而跑多了**。

原因：**每做一次对比，都要把"改之前"重跑一遍作对照。**
这个开销在小语料上占比很高（单次实验几十毫秒，但对比的固定成本下不来）。

所以这个工具的 `finish` 不会给你编一个漂亮的对比，它会**算出来再报**：

```
对照：你在 5 种切分窗口上探索。如果把每种窗口的所有组合都跑一遍，
是 5 × 3 种召回 × 2 种重排 = 30 次。
你跑了 16 次，省了 14 次。
```

没省就直说：

```
你跑了 16 次——**这次没比穷举省**。
原因是每做一次对比都要把「改之前」重跑一遍作对照，
而语料小、单次实验只要几十毫秒，这个开销占比就上来了。
维度一多（或者单次实验变贵）差距才会拉开。
```

### 自适应真正强的地方（不是省次数）

比"省几次实验"更重要的是这一条。

这次诊断最后停在 **「递归切分 200 字 · 仅关键词召回」，MRR 0.938**。

**而这个配置在基准里根本没出现过**——基准跑的是 120 字那一档。

它是这么走出来的：

```
基准 120 字      → 最好的组合是 120字 + 关键词，MRR 0.906
试"加重排"        → MRR 掉到 0.708，没用
试"切分改 200 字"  → MRR 跳到 0.938，有戏
试"切分改 300 字"  → 没更好
试"切分改 60 字"   → 变差
收尾
```

**这才是自适应探索的价值：不是把已知的几档跑一遍，
而是顺着中间结果走到没试过的地方。**

穷举只能覆盖你预先列出来的那几档。而"200 字"这个最优值，
如果没人告诉你要试，穷举也不会试。

### 它不下结论

这点容易忽略，但很重要。

整套设计里：

| 谁 | 干什么 |
|---|---|
| Agent（大模型） | **决定试什么**、把过程串起来讲 |
| 诊断引擎（固定规则） | **算指标、推结论** |

所以报告里"瓶颈在召回还是排序""切分有没有影响"这些话，
都是**规则从数字推出来的**，不是大模型写的。

为什么这么分？

因为结论要能拿去改生产配置。同一份数据、同一套测试集，
你今天跑和下周跑必须得到同样的说法。让大模型写结论就做不到这一点。

`finish` 工具的返回里会明确告诉你这件事：

```
这些结论由固定规则从指标推导，不经过大模型——
所以同样的数据每次都会得到同样的说法。
```

## 改一改试试

### 试 1：把轮数上限压到 3

```bash
java -jar ragsight-agent/target/ragsight-agent-exec.jar diagnose --max-iters 3
```

3 轮不够探索完。**看它被截断时怎么收尾**——这是实际用 Agent 常遇到的情况。

### 试 2：看它怎么处理"无效改动"

问它一个不可能有收益的改动，比如让它在当前最好已经是关键词召回时，
再"改成关键词召回"。它会回：

```
当前最好用的就是 keyword 召回，换另一个试试。
```

**这是工具在做校验，不是模型在判断。** 工具的返回值决定了模型下一步怎么走。

### 试 3（读代码）：看校验有多少

打开 `DiagnosisTools.java`，看 `validateChange` 那个方法。

你会发现"合法输入"的校验写得很细：不认识的值、改成当前值、
窗口比重叠还小……每一种都返回一句人能看懂的话。

**为什么？因为读这些文字的是模型。**
抛异常给它看堆栈，它只会瞎猜；给它一句"当前最好用的就是这个，换一个试试"，
它就知道该怎么办。

### 试 4（读代码）：看"当前最好"怎么更新

看 `DiagnosisSession` 里的 `runForComparison` 和 `applyIfBetter`。

这里有个我踩过的坑：最初对比时会一次性把整批结果拿去竞争"当前最好"，
结果**改之后变差时，"改之前"因为还在批里又被选回来了**——
表现上像是改动没生效。

现在拆成了"只跑不碰状态"和"显式更新最好"两步。

## 小结

1. **穷举跑不完**：维度一多就是组合爆炸，而且大部分组合没必要试。
2. **单变量对比是可归因的前提**：一次改一个，指标变了才知道是谁的功劳。
3. **自适应不一定更省**：每次对比都要重跑"改之前"，小语料上这个成本占比高。维度多、单次实验贵的时候才拉得开。
4. **它真正强的地方是"走到没试过的地方"**：这次找到的 200 字那一档，基准里没有。
5. **Agent 只决定试什么，不下结论**：结论由固定规则从数字推导，保证可复现。
6. **工具的返回值是给模型看的**：错误信息要写成"人能看懂的话"，不是抛异常。

---

## 常见误解

**"让 Agent 自己试，肯定比穷举省。"**

不一定，见上面。省不省要看维度数和单次实验成本。
**在小语料、快实验的场景下，老老实实穷举可能更简单。**

**"Agent 会自己找到最优解。"**

它找到的是"在它试过的范围里最好"的那个。
它可能错过最优解，也可能在某个方向过早放弃。
**它是个探索策略，不是优化算法。**

**"既然有 Agent 了，就不要固定规则了吧。"**

不行。这个项目坚持"Agent 决定试什么，规则决定结论"。
如果让模型写结论，你就失去了可复现性——而这是拿报告去做决策的前提。

**"Agent 的总结可以直接发给同事。"**

它的总结读起来很像样，但那是模型写的。
**要引用就引用"硬数据"那一段**（实验次数、推荐配置、指标），
那些是工具算出来的。

## 回头看

整个项目就是这两层：

```
第二层：决定试什么      ← 会调大模型，允许不确定
第一层：算指标、推结论   ← 纯计算，必须可复现
```

**分界线在"要不要可复现"。**

- "下一步试哪个"——试错也没关系，不确定可以接受
- "指标是多少、瓶颈在哪"——必须每次都一样，否则没人敢用

这条线画在哪，决定了整个架构。这也是为什么第一层的 core 里
一行大模型调用都没有，并且有架构测试盯着。
