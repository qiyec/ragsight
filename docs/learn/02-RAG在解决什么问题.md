# 02 RAG 在解决什么问题

## 这篇解决什么问题

**先搞清楚 RAG 在做什么，再谈怎么调它。**

很多人一上来就调 `chunk_size`、换向量库，但说不清 RAG 的三步各自负责什么。
结果就是：出了问题不知道该改哪一步。

---

## 先跑一下

用仓库里那份示例语料（4 篇虚构的 SaaS 产品文档）：

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt
```

（中文乱码就加 `-Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8`）

看报告里"逐用例明细"那一块，找到 `c004` 这一行：

```
| c004 | 4 | 4 | 4 | 5 | 2 | 3 | — | 4 | — |
```

**这一行里有一个 `—`。** 记住它，这篇要讲的就是它意味着什么。

---

## 看到了什么

先看这份语料里有什么。`examples/corpus/billing-rules.md` 里有一句：

```
账单会在次月 3 日前生成，可通过控制台的账单中心查看。
```

测试集里的 `c004` 是这么问的：

```
Q: 账单什么时候出
E: 次月 3 日前生成
```

**问题用"出"，文档用"生成"。**

这个差别很小，但它决定了你能不能检索到。下面会展开。

---

## 为什么是这样

### 大模型的两个硬伤

你先想一下：直接把问题丢给大模型，会有什么问题？

**第一，它不知道你的私有文档。**

你问"我们的账单什么时候出"，它不知道你们公司的规则是什么。
它可能给你一个"一般来说……"的回答。

**第二，它会编。**

这个更麻烦。大模型被训练成"给出一个看起来合理的回答"，而不是"不知道就说不知道"。
所以它编出来的东西读起来一样流畅，你很难分辨。

> 这个现象叫**幻觉**（hallucination）。业内叫法，就是这个意思。

### RAG 怎么解决

**RAG = Retrieval-Augmented Generation，检索增强生成。**

名字很长，做法很朴素：

> **先去你的文档里找出相关的几段，再把"问题 + 这几段"一起交给大模型，
> 让它基于这些材料回答。**

这样两个硬伤都缓解了：

| 硬伤 | RAG 怎么缓解 |
|---|---|
| 不知道私有文档 | 相关段落是从你的文档里找出来的，直接喂给它 |
| 会编 | 有材料在眼前，它可以照着材料说；材料里没有，你可以要求它说不知道 |

### 三个阶段

```
        ┌────────────────────────────────────────────┐
        │  1. 准备（离线做一次）                       │
        │     文档 ──切分──▶ 片段 ──向量化──▶ 存进索引  │
        └────────────────────────────────────────────┘
                            │
        ┌───────────────────▼────────────────────────┐
        │  2. 检索（每次提问时做）                     │
        │     问题 ──▶ 从索引里找最相关的 N 个片段      │
        └────────────────────────────────────────────┘
                            │
        ┌───────────────────▼────────────────────────┐
        │  3. 生成（每次提问时做）                     │
        │     「问题 + 找到的片段」──▶ 大模型 ──▶ 回答  │
        └────────────────────────────────────────────┘
```

**这个项目只诊断第 1、2 步。**

为什么？因为第 3 步的问题你能直接看出来——回答胡说八道，你一眼就知道。
但第 2 步出问题的时候，**表面上看不出来**：

- 检索回来的那段文字读起来挺相关的
- 大模型也确实基于它回答了
- 但那段根本不是正确答案所在的段落

**它答得很像，但是错的。** 这才是最难查的情况。

### 检索做不好会长什么样

回到开头那个 `—`。

`c004` 的意思是"账单什么时候出，答案在『次月 3 日前生成』这句里"。
在"固定窗口 90 字 + 仅向量召回"这一列，它是 `—`——**前 5 条里根本没有**。

也就是说：如果线上用的是这套配置，用户问"账单什么时候出"，
系统压根拿不到那句"次月 3 日前生成"。大模型只能靠编。

而在"递归切分 90 字 + 仅向量召回"下，它排第 4——**能拿到，但排得靠后**。

同一个问题、同一份文档、同一个向量模型，**只因为切分方式不同，
一个能检索到、一个检索不到**。

**而且原因不是"答案被切断了"。** 我一开始也这么以为，
去看真实片段才发现：两种切分下都有含答案的片段。

真正的原因是**片段里混进了别的内容**：

```
递归切分的片段：…账单会在次月 3 日前生成，可通过控制台的账单中心查看。
                （只讲账单周期，很纯）

固定窗口的片段：…账单会在次月 3 日前生成，可通过控制台的账单中心查看。
                计费项包括三部分：计算资源、存储空间和网络流量
                （还混进了"计费项"的内容，被稀释了）
```

固定窗口按字数硬切，凑满 90 字就断，不管语义到哪。
于是"账单周期"和"计费项"这两个不相干的内容被塞进同一个片段，
它的向量就变成了两者的混合——**问账单周期时，它没那么像了**。

这个项目里管这叫"语义被稀释"。第 3 篇会详细讲怎么避免。

这就是为什么需要工具来量：光看代码看不出来，光看回答也看不出来。

### 试 1：对比两种切分，看 c004 的命运

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt
```

在明细表里找 `c004`，横向对比这几列：

```
recursive-90/vector   → 4
recursive-200/vector  → 5
fixed-90/vector       → —
```

**同一个问题，切分方式一变，从"排第 4"变成"完全没有"。**

### 试 2：横向看三种召回

还是同一份报告，看 `c004` 这一行在"递归切分 90 字"那三列：

```
recursive-90/vector   → 4
recursive-90/keyword  → 4
recursive-90/hybrid   → 4
```

问题用"出"、文档用"生成"——关键词召回居然也能排到第 4。
因为它匹配上了"账单"这个词。**关键词召回靠字面重合，
哪怕只重合一个词，也有机会。**

但换个问题它就不行了。这个留到第 4 篇讲。

## 小结

1. **RAG = 先找材料，再让模型基于材料回答。** 解决"不知道私有文档"和"会编"两个问题。
2. 三个阶段：**准备（切分+入库）、检索、生成**。前两个是离线/在线，第三个是模型的事。
3. **这个项目只诊断检索阶段。** 生成阶段的问题你能直接看出来，检索阶段的问题看不出来。
4. 检索出问题时，表现不是"答不出来"，而是**"答得很像但是错的"**——这是最难查的。
5. 同一个问题，切分方式一变，可能从"能检索到"变成"完全检索不到"。

---

## 常见误解

**"RAG 嘛，就是向量数据库 + 大模型。"**

这句话漏掉了最容易出问题的部分：**切分**。
向量数据库负责"存和找"，但"往里存什么"是切分决定的。
切得不好，向量库再好也找不着——上面 `c004` 那个 `—` 就是这么来的。

**"检索回来的内容看着挺相关的，应该没问题。"**

"看着相关"和"包含答案"是两件事。
问"账单什么时候出"，返回一段讲"计费项包括三部分"的文字，
读起来很相关，但里面有答案吗？没有。

**"我可以让大模型自己判断检索得好不好。"**

这就把"量"变成了"猜"。而且不稳定：同一份数据，模型这次说好、下次说一般。
这个项目的所有结论都是**用固定公式从数字算出来的**，就是为了避免这个问题。
