# 01 跑起来看结果

## 这篇解决什么问题

**先搞清楚这个工具的输出长什么样，以及每一块在回答什么问题。**

不理解输出，后面的原理都是空谈。所以第 1 篇不解释原理，只看东西。

---

## 先跑一下

```bash
# 如果你还没打包
mvnw.cmd clean package -DskipTests     # Windows
./mvnw clean package -DskipTests       # macOS / Linux

# 跑内置演示语料（不用准备任何数据）
java -jar ragsight-cli/target/ragsight-cli.jar diagnose
```

Windows 上如果中文乱码，加两个参数：

```bash
java -Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8 -jar ragsight-cli/target/ragsight-cli.jar diagnose
```

**第一次运行前请先看一眼**：它用的是"离线哈希向量化"，不联网、不用 Key。
它的能力有限（只认字面重合），所以**绝对分数没有参考价值**。
这一点报告之外的提示里也写了：

```
向量化方式：离线哈希，只认字面重合，所以下面的绝对分数不代表真实向量模型的效果
想看真实效果，加 --embedding-model（见 --help）
```

但**流程、结构、怎么读报告，现在就能学**。等你看完第 6 篇再接真实模型也不迟。

---

## 看到了什么

输出分七块。按顺序看。

### 第 1 块：头部元信息

```
- **语料**：演示语料：SaaS 产品帮助中心
- **测试集**：10 个用例（含 2 个负样本）
- **对比维度**：3 种切分 × 3 种召回 = 9 次实验
- **基准**：递归切分 90 字 + 仅向量召回（报告里的差值都是相对它算的）
```

**这一块在回答：这次诊断是在什么条件下跑的。**

四个信息都重要：

| 信息 | 为什么重要 |
|---|---|
| 语料 | 换一份文档，所有数字都变。看报告先看它量的是哪份 |
| 测试集 | 用例数太少的话，指标波动很大 |
| 对比维度 | 知道跑了多少次实验 |
| **基准** | **后面所有差值都是相对它算的**，不看清基准，差值的正负就没意义 |

最后那条特别容易忽略。报告里说"某个方案 MRR +0.15"，
意思是"比基准高 0.15"，不是"MRR 是 0.15"。

### 第 2 块：片段数统计

```
各切分方案切出的片段数：递归切分 90 字 → 14 个片段；
递归切分 200 字 → 6 个片段；固定窗口 90 字 → 14 个片段
```

**这一块在回答：每种切分把文档切成了多少块。**

为什么要单独列出来？因为这直接影响后面数字的可比性。

看这两个：

- 递归切分 90 字 → **14 个片段**，召回前 5 条 = 拿到 5/14 ≈ 36% 的内容
- 递归切分 200 字 → **6 个片段**，召回前 5 条 = 拿到 5/6 ≈ 83% 的内容

**同样是"取前 5 条"，第二种情况几乎把整个知识库都塞给模型了。**

所以报告里有一句提醒：

```
> 但别急着下结论：片段切得越大，一个片段里装的内容越多，
> 命中率天然就越高——这不一定说明检索变好了。
```

这是这个工具最想让人记住的一件事。

### 第 3 块：诊断结论

```
- 4 个文档，10 个用例（负样本 2 个），共跑 9 次实验
- 基准（递归切分 90 字 + 仅向量召回）Recall@5 = 0.900，
  召回基本够用，瓶颈更可能在排序环节。
- 切分确实有影响：「递归切分 200 字」的 Recall@5 最高（1.000），比其他切分方案至少高 0.100。
- ⚠ 但别急着下结论：……
- 以下方案相对基准没什么变化（提升都小于 0.05），不值得为此增加复杂度：向量+关键词 融合
```

**这一块在回答：所以结论是什么，下一步该改哪里。**

注意这里的写法：**每条结论都附了具体数字**。

不是"召回效果一般"这种话，而是"Recall@5 = 0.900，召回基本够用"。
这样你才能判断它说得对不对。

> **一个关键设计**：这些结论是**用固定规则从数字推出来的，不是大模型写的**。
> 所以同一份数据、同一套测试集，你跑两次得到的是同一份结论文本。
>
> 为什么这么设计？因为这个工具是拿来改生产配置的。结论不稳定，人就不敢用。

### 第 4 块：指标对比表

```
### 递归切分 90 字（14 个片段）

| 召回方式 | Recall@5 | MRR@5 | nDCG@5 |
|---|---|---|---|
| 仅向量召回 **(基准)** | 0.900 | 0.646 | 0.694 |
| 仅关键词召回 | 0.900 | 0.813 | 0.829 |
| 向量+关键词 融合 | 0.900 | 0.688 | 0.737 |
```

**这一块在回答：每种组合的具体分数是多少。**

按切分方案分组。**同一组内可以直接比**（切分一样、片段数一样），
跨组就要留意片段数已经变了（见第 2 块）。

三个指标后面第 5 篇细讲，这里先记住一句话：

| 指标 | 回答什么问题 |
|---|---|
| Recall@5 | 该找到的东西，**找到了吗** |
| MRR@5 | 找到的那条，**排得靠前吗** |
| nDCG@5 | **整体排序质量**好不好 |

### 第 5 块：相对基准的变化

```
| 实验 | Recall@5 | MRR@5 | nDCG@5 |
|---|---|---|---|
| 递归切分 200 字 + 仅关键词召回 | +0.100 | +0.292 | +0.260 |
| 递归切分 90 字 + 仅关键词召回 | ±0.000 | +0.167 | +0.135 |
```

**这一块在回答：每个方案比"现在的配置"好多少。**

注意是**相对基准**，不是绝对值。之所以单独列一块，是因为人看绝对值不容易判断好坏——
0.813 是好还是不好？不知道。但"+0.167"就很直观。

报告里还有一句判断标准：

```
> 差值是「这次实验 − 基准」。正数表示更好。
> 变化小于 0.05 通常不值得为它增加系统复杂度。
```

**0.05 这个门槛是有意的**：指标提升一点点，可能只是测试集噪声，
但为了它引入融合召回、引入重排，成本是实打实的。

### 第 6 块：逐用例明细

```
| 用例 | recursive-90/vector | recursive-90/keyword | ... |
|---|---|---|---|
| c001 | 1 | 1 | ... |
| c004 | 4 | 4 | ... |
| c009 | n/a | n/a | ... |
```

**这一块在回答：具体哪个问题出问题了。**

格子里的数字是"期望片段的最好排名"：

- `1` = 第一个就是答案
- `4` = 排到第 4 才有
- `—` = 前 K 条里没有（**没召回到**）
- `n/a` = 负样本（这题本来就没有答案）

**这一块是排查问题的入口。** 指标是平均分，平均分不好看时，
你得知道是"所有问题都差一点"还是"少数问题差得多"——这两种情况的改法完全不同。

### 第 7 块：实验标识对照

```
- `recursive-90/vector` = 递归切分 90 字 + 仅向量召回
```

明细表的表头为了不撑爆，用了短 id。这块是翻译表。

## 为什么是这样

看完七块，你会发现整份报告的结构就是一条思路：

```
先交代条件（第 1、2 块）
  → 给结论（第 3 块）
  → 给证据（第 4、5 块）
  → 给下钻入口（第 6 块）
```

**这个顺序不是随手排的。** 它对应你实际排查问题时该问的顺序：

1. 这次量的是哪份文档、什么条件？
2. 结论说什么？
3. 依据的数字是什么？
4. 哪个具体用例拖后腿？

反过来（先看明细表）容易一叶障目：某个用例表现差，
可能只是这条用例标得有问题，不代表整体。

## 改一改试试

### 试 1：只跑一个切分方案

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose --only-chunking
```

实验次数会从 9 次变成 3 次（1 种切分 × 3 种召回）。

**注意它做的不是"只对比切分"**，而是"只跑一个切分方案、不和别的切分比"——
为了快点看到结果用的。这时候报告里就不会出现"切分有没有影响"那条结论了：
只跑一种切分，无从比较。

这一点值得留意：**结论的覆盖面取决于你跑了什么**。
没跑两种切分，就不能指望工具告你切分有没有影响。

### 试 2：把召回条数从 5 改成 3

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose --top-k 3
```

`topK` 变小，Recall 通常会降。**看报告里"片段数 vs topK"的关系有没有变。**

### 试 3：把切分窗口调到极大

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose --chunk-size 500
```

片段会变得很少。这时候看 Recall——**通常会接近满分**。

然后问自己：**这是检索变好了，还是"取前 5 条"已经差不多等于"返回全部"？**

这就是第 3 块那条 ⚠ 提醒在说的事。

---

## 小结

1. 报告分七块，顺序是"条件 → 结论 → 证据 → 下钻"，对应排查问题的思路。
2. **基准要看清**。所有差值都是相对它算的。
3. **片段数决定数字能不能直接比**。跨切分方案比较时要留意。
4. **结论文本由规则推导，不是大模型写的**——这是结果可复现的前提。
5. 平均分不好看时，先去第 6 块看是"普遍差一点"还是"少数差很多"。

---

## 常见误解

**"报告说 Recall 1.000，所以我的 RAG 没问题。"**

不一定。`Recall@5 = 1.000` 只说明"该找到的都进了前 5 条"。
但如果片段总数本来就少于 5，这个 1.000 是白送的——取前 5 条等于返回全部。

**"指标越高越好，所以我要把 topK 调到 20。"**

topK 大了，Recall 会涨（废话，找的东西多了），但你喂给大模型的上下文也变长了，
里面混进的无关内容更多。**召回率和上下文质量是矛盾的**，不是越大越好。

**"这个工具说我的切分有问题，那我就把片段切大。"**

片段切大确实会让命中率涨，但那是"一个片段装的内容多"带来的，
不是"检索变精准"带来的。而且片段越大，模型拿到的无关内容越多。
报告里那条 ⚠ 就是拦这个的。
