# 05 指标：怎么判断好不好

## 这篇解决什么问题

**"我的 RAG 效果好不好？"** 这个问题没有单个数字能回答。

这篇讲三个指标各自回答什么问题，并且**带你手算一遍**——
算完你就不会再被"某个指标 0.85"这种数字唬住。

---

## 先跑一下

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt
```

看"指标对比"表里"递归切分 90 字"那一组：

```
| 召回方式 | Recall@5 | MRR@5 | nDCG@5 |
|---|---|---|---|
| 仅向量召回 **(基准)** | 1.000 | 0.688 | 0.765 |
```

**同一批结果，三个数字差很多。** 这篇讲为什么。

---

## 为什么一个指标不够

先看一个具体的失败场景。

你问"账单什么时候出"，正确的那段排在第 4 位，前 3 位都是别的。

现在问：这算成功还是失败？

| 看法 | 结论 |
|---|---|
| 它在前 5 条里，模型能看到 → | 成功 |
| 它排第 4，模型可能被前 3 条带偏 → | 打折扣 |
| 理想是排第 1，现在第 4 → | 不理想 |

**三种看法都对，所以三个指标。**

| 指标 | 回答的问题 | 关心什么 |
|---|---|---|
| **Recall@k** | 该找到的，**找到了吗** | 有没有漏 |
| **MRR@k** | 找到的那条，**排得靠前吗** | 第一条对的排第几 |
| **nDCG@k** | **整体排序**好不好 | 全部相关项的位置 |

## 手算一遍

光看公式记不住。拿真实数据算一遍，算出来的数和工具显示的**一模一样**，
你就有底气了。

### 拿到的原始数据

这是"递归切分 90 字 + 仅向量召回"的逐用例排名（从报告的明细表里抄的）：

| 用例 | 排名 | 说明 |
|---|---|---|
| c001 | 1 | |
| c002 | 1 | |
| c003 | 4 | |
| c004 | 4 | |
| c005 | 1 | |
| c006 | 2 | |
| c007 | 1 | |
| c008 | 2 | |
| c009 | n/a | 负样本 |
| c010 | n/a | 负样本 |

**注意负样本怎么处理——三个指标不一样。** 这一点很容易记错（我第一版文档就写错了）：

| 指标 | 负样本返回什么 | 分母里算不算它 |
|---|---|---|
| Recall@k | **1.0**（算命中） | **算** |
| MRR@k | NaN（跳过） | 不算 |
| nDCG@k | NaN（跳过） | 不算 |

**为什么 Recall 要给负样本算满分**：负样本是"知识库里本来就没有答案"的问题。
既然没有该找的东西，就**不存在"漏找"**。给它判 0 分是错的（它没做错什么），
给它满分才符合"召回率 = 该找到的都找到了"这个定义。

**为什么 MRR/nDCG 要跳过**：这两个衡量"排序质量"。
负样本没有"正确答案该排第几"这回事，排序质量对它无定义。
所以返回 NaN，让平均时跳过它。

**这个差别会在数字上体现出来**，一定要记住。

### Recall@5

**定义：每条用例算"命中的期望片段 / 期望片段总数"，再对所有用例求平均。**
负样本算 1.0，所以分母是全部 10 条用例。

这 8 条正样本全都排在前 5，各得 1.0；2 条负样本也得 1.0：

```
(8×1.0 + 2×1.0) / 10 = 10 / 10 = 1.000
```

工具显示：`1.000` ✅

> 如果有一条是 `—`（前 5 条里没有），它就贡献 0。
> 一条没命中，Recall 就掉 0.1（10 条用例里的一条）。

### MRR@5

**定义：每条用例取"1 / 排名"，然后对**正样本**求平均（负样本跳过）。**

分母是 **8**（只有正样本）：

```
c001: 1/1 = 1.0
c002: 1/1 = 1.0
c003: 1/4 = 0.25
c004: 1/4 = 0.25
c005: 1/1 = 1.0
c006: 1/2 = 0.5
c007: 1/1 = 1.0
c008: 1/2 = 0.5
```

加起来：

```
1.0 + 1.0 + 0.25 + 0.25 + 1.0 + 0.5 + 1.0 + 0.5 = 5.5
```

除以 8：

```
5.5 / 8 = 0.6875
```

工具显示：`0.688` ✅（四舍五入）

> **MRR 的含义**：如果所有用例都排第 1，MRR = 1.0。
> 有一条排第 4，它就把平均拉低不少——因为 1/4 只有 0.25。

### nDCG@5

**定义：每条用例取"1 / log₂(1 + 排名)"，然后对**正样本**求平均。**
分母同样是 8。

（严格定义里还有"多个相关项"的处理，这个项目每条用例只标一个期望片段，
所以公式简化成这样。）

`log₂` 是"以 2 为底的对数"。先记几个值：

| 排名 | log₂(1+排名) | 1 / log₂(1+排名) |
|---|---|---|
| 1 | log₂(2) = 1.000 | 1.000 |
| 2 | log₂(3) ≈ 1.585 | 0.631 |
| 3 | log₂(4) = 2.000 | 0.500 |
| 4 | log₂(5) ≈ 2.322 | 0.431 |
| 5 | log₂(6) ≈ 2.585 | 0.387 |

代进去：

```
c001: 排名 1 → 1.000
c002: 排名 1 → 1.000
c003: 排名 4 → 0.431
c004: 排名 4 → 0.431
c005: 排名 1 → 1.000
c006: 排名 2 → 0.631
c007: 排名 1 → 1.000
c008: 排名 2 → 0.631
```

加起来 = 6.124，除以 8：

```
6.124 / 8 ≈ 0.765
```

工具显示：`0.765` ✅

### 三个数都算对了

| 指标 | 你算的 | 工具显示的 |
|---|---|---|
| Recall@5 | 1.000 | 1.000 |
| MRR@5 | 0.6875 | 0.688 |
| nDCG@5 | 0.765 | 0.765 |

**这就是"可复现"的意思**：公式固定、数据固定，谁算都是这个数。

## 三个指标怎么配合看

现在有了真实数字，看看怎么用。

### 场景 A：Recall 低

```
Recall@5 = 0.600, MRR@5 = 0.700
```

有 40% 的用例**压根没进前 5**。
这时 MRR 0.700 是好是坏？**根本不重要**——漏掉的那 40%，排序再好也没用。

**先解决召回。** 报告里也会这么说：

```
基准（……）Recall@5 = 0.600，召回不够：约 40% 的期望片段没进候选。
```

（这是报告里的真实措辞：把"没进候选的比例"直接算给你。）

### 场景 B：Recall 高、MRR 低

```
Recall@5 = 1.000, MRR@5 = 0.400
```

东西都找到了，但排得乱七八糟。这就是上面手算那个数据的样子（MRR 0.688）。
**这是排序问题，解决办法是加重排，不是继续调切分。**

### 场景 C：三个都低

```
Recall@5 = 0.400, MRR@5 = 0.300, nDCG@5 = 0.320
```

召回就有问题。先看数据本身：文档在不在库里？切分是不是把答案切碎了？

### 为什么 nDCG 和 MRR 要并存

MRR 只看**第一个**相关项的位置。如果一条用例只标了一个答案，两者高度相关。

但如果一个问题的答案分散在多处（"列出所有计费项"），
MRR 对第二个、第三个答案排在哪儿完全不敏感，nDCG 会。

这个项目的测试集每条用例标一个期望片段，所以两者数字比较接近。
**线上真实场景里，如果你标了多个答案，两者会拉开。**

## 负样本：为什么三个指标处理方式不同

测试集里有两类用例：

```
Q: 错误码 E4021 是什么意思
E: E4021 表示计费账户被冻结          ← 有答案（正样本）
```

```
Q: 如何申请退款                       ← 知识库里没有这个
（没有 E: 行）                        ← 负样本
```

上面那张表总结了处理方式，这里说为什么：

**Recall 给负样本满分 1.0。**
"召回率"的定义是"该找到的东西找到了多少"。
负样本没有该找的东西，所以**不存在漏找**。
判它 0 分是冤枉它（它没做错什么），判满分才符合定义。

**MRR / nDCG 跳过负样本（返回 NaN）。**
这两个衡量排序质量。"正确答案该排第几"对负样本不存在，所以无定义。

明细表里负样本显示 `n/a`，就是这个意思。

**负样本不能没有。** 如果你只测"有答案的问题"，
一个"永远返回最相似那一条"的检索器也能拿满分——
反正每个问题都有"最相似的那一条"，它永远能返回点什么。

负样本用来暴露这种"硬凑"。但这个项目的三个指标都**不直接惩罚负样本**——
它们只负责量"有答案的问题答得怎么样"。负样本的作用体现在别处
（下一篇文章讲怎么用它）。

> 这是个可以深挖的点：严格说"检索器对无答案的问题应该返回空或低分"，
> 但怎么量这件事，业界还没有像 Recall/MRR 那样统一的口径。
> 这个项目选择不发明新指标，而是把负样本摆出来让人自己看。

### 试 1：自己算一遍

从报告明细表抄下"递归切分 90 字 + 仅关键词召回"那一列的排名，
按上面的方法算 Recall、MRR、nDCG，和报告里的对一下。

关键词召回那一组的数字是：

```
| 仅关键词召回 | 1.000 | 0.823 | 0.866 |
```

**先别看答案，自己算。** 算完再对。

### 试 2：把 topK 改成 2，看哪个指标跌得最狠

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt --top-k 2
```

我实测的结果（只看向量召回）：

| | Recall@5 | MRR@5 | nDCG@5 |
|---|---|---|---|
| `topK=5` | 1.000 | 0.688 | 0.765 |
| `topK=2` | **0.800** | **0.625** | **0.658** |

**Recall 跌得最明显**（1.000 → 0.800）：原来排第 4 的那两条（c003、c004）出局了。

**先自己预测再跑**，这种习惯比看十遍公式有用。

### 试 3：看一条用例出局的影响

在明细表里找 `—`（前 K 条没有）。

`topK=2` 时有两条出局，Recall 从 1.000 掉到 0.800 ——
**掉 0.2，正好是 2/10**。

**一条用例没命中，Recall 掉 0.1（10 条用例里的一条）。**
这就是为什么测试集不能太小：10 条用例里错一条，分数就掉 10%，噪声很大。

## 小结

1. **三个指标回答三个问题**：找到了吗（Recall）、排得靠前吗（MRR）、整体排序好吗（nDCG）。
2. **Recall 是上限**。它低的时候，另外两个指标没有意义。
3. **MRR 只看第一个对的**。多个正确答案时，它对后面的不敏感，nDCG 才敏感。
4. **负样本的处理三个指标不一样**：Recall 给满分（不存在漏找），MRR/nDCG 跳过（排序质量无定义）。
5. **公式固定、数据固定，结果就固定**。这是这个工具能用来做决策的前提。

## 常见误解

**"MRR 0.7 算好吗？"**

没有上下文没法回答。要看：
- Recall 是多少（如果 Recall 只有 0.6，MRR 0.7 是虚的）
- 用例多少（10 条用例的 0.7 和 1000 条用例的 0.7 置信度完全不同）
- 任务性质（FAQ 检索要求排第 1，宽泛搜索排前 5 就够）

**"我用 Recall@10，看起来比 Recall@5 高很多。"**

废话——`k` 越大越容易中。跨报告比较时必须用**同一个 k**。
而且 `k` 大了，喂给模型的上下文也长了，未必是好事。

**"三个指标都算一下，取平均当总分。"**

别这么干。它们不是独立的、可加权的量。
Recall 低的时候 MRR 再高也没意义，平均一下反而把问题掩盖了。
**按顺序看：先 Recall，再 MRR，最后 nDCG。**

**"nDCG 比 MRR 复杂，所以更准。"**

不是"更准"，是"看的东西不同"。单答案场景下 MRR 足够，多答案场景才需要 nDCG。
