# 04 召回：两种方法为什么都要

## 这篇解决什么问题

**"该用向量召回还是关键词召回？"** 这是面试高频问题，也是线上必做的选择。

这篇用真实数据说明：**两者擅长的是不同的东西**，所以答案取决于你的用户会怎么问。

---

## 先跑一下

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt
```

看"逐用例明细"里这两行：

```
| c003 | 4 | 1 | 2 | ...    ← 错误码 E4023
| c004 | 4 | 4 | 4 | ...    ← 账单什么时候出
```

三列分别是：仅向量召回、仅关键词召回、向量+关键词 融合。

**`c003` 上关键词明显强（1 vs 4），`c004` 上两者打平（4 vs 4）。**

这两个数字背后是两种完全不同的匹配方式。

---

## 看到了什么

同一份语料，我把两条典型用例拎出来（列是"排第几"，1 最好）：

| 用例 | 问题 | 期望答案 | 向量召回 | 关键词召回 |
|---|---|---|---|---|
| c003 | 错误码 E4023 代表什么 | E4023 表示计费项配置冲突 | 4 | **1** |
| c004 | 账单什么时候**出** | 次月 3 日前**生成** | 4 | 4 |

- **c003 是精确编号**：问题里就带着 `E4023`。关键词召回直接命中，排第 1。
- **c004 是同义改写**：用户说"出"，文档写"生成"。关键词召回对不上，排到第 4。

**这就是两种召回的分工。**

---

## 为什么是这样

### 关键词召回（BM25）在做什么

它统计**词**：

- 这个词在这篇文档里出现了几次？
- 这个词在整个语料库里有多罕见？

**越罕见的词，命中它越值钱。**

`E4023` 这种编号在整个语料里只出现在一个地方——命中它，几乎可以断定就是这篇。
而"的""是""了"到处都是，命中它们等于没命中。

所以关键词召回在**专有名词、错误码、产品型号、人名**这类"精确字符串"上特别强。

**它的短板也很明确**：它只认字面。

用户问"账单什么时候出"，文档写"账单生成时间"——**一个字都不一样**，
关键词召回完全无法把它们联系起来。

### 向量召回（Embedding）在做什么

它先把文字变成一串数字（向量），然后比"两个向量有多接近"。

**关键：意思相近的文字，向量也接近。** 哪怕用词完全不同。

所以它能处理"出" ↔ "生成"、"怎么配" ↔ "配置流程"这类同义改写。

**它的短板是**：对精确字符串不敏感。

`E4023` 和 `E4023` 当然一样，但 `E4023` 和 `E4024` 在向量空间里也**很接近**——
一个数字的差别，向量几乎看不出来。

所以纯向量召回时，问 `E4023` 可能把讲 `E4024` 的文档也排上来。

### 那为什么不全用融合？

看起来"两个都用"应该最好。但实测下来不是：

| 切分方案 | 向量 | 关键词 | 融合 |
|---|---|---|---|
| 递归 90 字 | 0.688 | **0.823** | 0.781 |
| 递归 200 字 | 0.838 | **0.938** | 0.854 |

融合的分数**卡在两者中间**——比关键词差，比向量好。

为什么？因为融合是把两份排名合起来（这个项目用 RRF），
**它拿不到"某一种方法特别好"的那部分优势，反而会被另一种方法的错误排名拉低**。

所以报告里经常出现这条结论：

```
以下方案相对基准没什么变化（提升都小于 0.05），
不值得为此增加复杂度：向量+关键词 融合
```

**融合不是免费的好事。** 它要多维护一套索引、多一次查询、多一层调参
（两路各取多少条、融合参数怎么定）。没有明显收益就不该上。

---

## ⚠️ 重要：上面这些数字是"离线哈希"跑出来的

**这一篇的结论有一半不能用。** 必须说清楚。

这个项目默认用的"向量化"叫**离线哈希**——它不联网、不用 Key，
但**它并不是真的语义模型**，只是把文字按字符散列成一串数字。

后果：**它只认字面重合，没有语义泛化能力。**

把它当"向量召回"的代表会得出错误结论。看这组对比：

| 用例 | 问题 | 离线哈希 向量/关键词 | 真实模型 向量/关键词 |
|---|---|---|---|
| c003 | 错误码 E4023 | 4 / **1** | **1** / 1 |
| c004 | 账单什么时候出 | 4 / 4 | **1** / 4 |

两处关键差别：

1. **c003**：真实模型下向量也能排第 1（离线哈希只能排第 4）。
   因为真实模型见过大量代码和编号，知道 `E4023` 是个整体，不是三个字。
2. **c004**：真实模型下向量排第 1，而**关键词还是第 4**（对不上"出"和"生成"）。

**换真实模型之后，"哪种召回更好"的答案变了。**

如果你照着离线哈希的结论去选召回方式，很可能选错。
这正是报告里一直挂着那句提示的原因：

```
向量化方式：离线哈希，只认字面重合，所以下面的绝对分数不代表真实向量模型的效果
想看真实效果，加 --embedding-model（见 --help）
```

想接真实模型，见 [README 里那一节](../../README.md#换成真实的向量模型)。

## 改一改试试

### 试 1：看 c004 在两种召回下的差别

```bash
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt
```

看 `c004` 这一行：向量=4、关键词=4。两个都排到第 4——但原因完全不同：

- 向量：离线哈希只认字面，"出"和"生成"对不上
- 关键词：同样对不上

**所以这条用例在离线模式下是"全员失败"的。** 接真实模型才能看到差别。

### 试 2：换一条能体现差别的

看 `c003`（错误码）：向量=4、关键词=1。

这条能体现差别，因为 `E4023` 是精确字符串，关键词直接命中。
而离线哈希把 `E4023` 打散成几个字符的散列，反而不如关键词准。

### 试 3（需要 Key）：接真实模型重跑

```bash
$env:RAGSIGHT_API_KEY = "你的key"
java -jar ragsight-cli/target/ragsight-cli.jar diagnose \
     --corpus examples/corpus --eval examples/eval.txt \
     --embedding-model text-embedding-v4
```

看 `c004` 从 4 变成 1。**这是"语义匹配"真正生效的样子。**

## 小结

1. **关键词召回**（BM25）统计词频和词的罕见程度，擅长精确字符串：错误码、型号、专名。
2. **向量召回**（embedding）比语义接近度，擅长同义改写：同义词、换说法。
3. **两者短板互补**，但**融合不一定有收益**——它常卡在两者中间，还多一层复杂度。
4. **离线哈希不是真的语义模型。** 它的"向量召回"只认字面，不能用来判断"该不该用向量召回"。
5. 判断该用哪种，看你的用户**怎么问**：带着编号问 → 关键词；换个说法问 → 向量。

---

## 常见误解

**"向量召回更先进，应该都用向量。"**

不一定。用户如果经常输入错误码、订单号、产品型号这类精确字符串，
关键词召回反而更准。而且关键词召回不需要模型、不需要调 API、延迟低。

**"那就两个都上，融合一下总不会更差。"**

实测就是更差（或者只是中间水平）。
多一路召回意味着多一次查询、多一套索引、多一堆参数要调。
**没有明确收益的复杂度是负债。**

**"BM25 是老技术，过时了。"**

BM25 诞生于 1990 年代，但今天仍然是检索系统的标配基线。
很多号称"纯向量"的系统，线上还是悄悄加了关键词兜底。

**"我用了向量召回，所以处理同义词没问题。"**

前提是你的 embedding 模型真的懂这些同义词。
如果模型没见过你行业里的术语（或者像离线哈希这样只认字面），
它一样对不上。
