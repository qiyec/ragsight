### 两类测试特别值得看

**手算验证的**（`Bm25ScorerTest`、`RetrievalMetricsTest` 等）：
每个用例的注释里都写了公式推导过程。这类测试才真正证明
"算得对"，而不是"代码没改"。

**验证诊断结论的**（`DiagnosisEngineChunkingTest`）：
用假召回器造出已知缺陷（比如"某个用例召回不到"），
断言引擎能诊断出来。这是**元评测的雏形**——
诊断工具最大的风险不是功能少，而是给出错误结论、用户还照着改了生产配置。

## 找类的时候

包名有规律：

- `domain.knowledge` —— 文档相关
- `domain.retrieval` —— 召回相关
- `domain.evaluation` —— 指标相关
- `application` —— 用例编排，不分子包（文件不多）
- `infra.<能力>` —— 按提供的能力分（embedding / index / reader / retriever / reranker / tokenizer）
- `cli.<用途>` —— command / demo / report

命名习惯：

- 接口名是**名词**：`Retriever`、`Tokenizer`、`Metric`
- 纯算法类叫 **`XxxScorer`** 或 **`XxxFusion`**：`Bm25Scorer`、`ReciprocalRankFusion`
- 实现类用**具体手段**命名：`FixedWindow...`、`DeterministicHash...`、`OpenAiCompatible...`
- 数据类几乎都是 `record`
