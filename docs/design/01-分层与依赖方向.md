# 分层与依赖方向

这篇讲五个模块各自的职责，以及**为什么依赖只能朝一个方向走**。

---

## 五个模块

```
ragsight-parent
├── ragsight-domain               核心逻辑：算法、模型、规则
├── ragsight-application          用例：把几步串成"一次诊断"
├── ragsight-infrastructure       实现：调模型、读写文件、建索引
├── ragsight-cli                  入口：命令行、报告渲染
└── ragsight-architecture-tests   门禁：用测试守住下面的规矩
```

---

## 依赖方向

```
     cli
      │
      ▼
 infrastructure ──▶ application
      │                  │
      └──────────────────┴──▶ domain
```

**所有箭头都指向 domain，没有一根反向的。**

具体说：

| 模块 | 可以依赖 | 不许依赖 |
|---|---|---|
| `domain` | 只有 JDK | 任何第三方库、其他模块 |
| `application` | `domain`、JDK | `infrastructure`、`cli`、任何第三方库 |
| `infrastructure` | `application`、`domain`、JDK、第三方库 | `cli` |
| `cli` | 全部 | —— |

---

## 为什么依赖只能单向

### 理由一：核心逻辑必须能独立验证

`domain` 里放的是"给定输入必然得到同样输出"的东西：切分算法、
BM25 打分、RRF 融合、三个指标的计算。

这些东西的正确性不能靠"跑起来看着像是对的"来判断，
得用**手算的数字**去核对。要能这么做，前提是它们能被独立跑起来——
不需要网络、不需要数据库、不需要 API Key。

而 `application` 之所以只依赖 `domain`，也是同一个道理：
诊断流程本身（"跑 N 种组合、算指标、推结论"）应该能在
没有任何真实实现的情况下被完整测试。

> 事实上这组测试是有的：`DiagnosisEngineChunkingTest` 用了假召回器，
> 精确控制"哪个用例命中、排第几"，从而构造出各种已知缺陷场景，
> 检查引擎能不能诊断出来。不依赖 `domain` 之外的任何东西。

### 理由二：换实现不该动核心

想把向量库从内存换成 pgvector、把模型从 DashScope 换成别的、
把文档格式从 Markdown 换成 PDF——这些都不该碰算法。

做到这一点的方法很朴素：**需要外部能力的地方定一个接口，
接口放在 domain，实现放在 infrastructure。**

比如：

```
domain/retrieval/EmbeddingModel    ← 接口：文本转向量
infra/embedding/DeterministicHashEmbedding   ← 实现一：离线哈希
infra/embedding/OpenAiCompatibleEmbedding    ← 实现二：调真实接口
```

domain 完全不知道有几种实现，也不知道它们怎么工作。

### 理由三：约束不靠人自觉

光写"不许依赖"没用，时间一长总有人顺手 import 一下。

所以有 `ragsight-architecture-tests` 模块，用 ArchUnit 把规矩变成测试：

| 规则 | 检查什么 |
|---|---|
| `domain_不应依赖任何第三方库` | domain 里的类只能引用 `java..` 和自己 |
| `domain_不应依赖常见便利库` | 点名校验 Jackson / Lombok / Guava / Spring / SLF4J 等 |
| `application_只能依赖_domain` | application 不许碰 infrastructure |
| `domain_不应使用随机数` | 不许出现 `Random` / `SecureRandom` |
| `domain_不应依赖基础设施` | 依赖方向不许反过来 |

违反了 `mvn verify` 就会失败。

这些规则自己也配了测试（`ArchGateSelfCheckTest`）——故意写两条
一定会失败的规则，确认门禁真的会拦人。不然规则写错包名、
或者包被改名之后，它会**静默失效**：构建照样通过，但实际什么都没检查。
这种"以为有门禁、其实没有"的状态比没有门禁更危险。

---

## 关于"不许用随机数"这条

看起来有点奇怪，值得单独说。

**诊断结论必须可复现。** 同一份文档、同一套测试集，跑两次必须得到
一模一样的数字。如果指标计算里混进了随机性，报告就不可信了。

而用户是要**拿这份报告去改生产配置**的。结论不稳定，他不敢用，
那这个工具就没有意义了。

所以 domain 层里：

- 排序遇到同分时，必须按一个固定的次级键（比如片段标识）来定顺序，
  不能"保持原顺序"——原来的顺序可能本身就不稳定
- 不许用随机数做任何事，包括采样、初始化
- 不许调大模型——模型的输出天然不确定

第 3 条也解释了为什么"结论由固定规则推导"。让大模型来写结论是很容易的，
但那样每个数字都得再验证一遍，工具就失去了立身之本。

## 一个具体的例子：域名层怎么保持零依赖

以 BM25 为例。BM25 是纯算法（词频、逆文档频率、长度归一化），
放 domain 很自然。但它需要**分词**，而分词在实践中往往要引入
HanLP、jieba、Lucene 这类库。

两难：算法该在 domain，但算法的前置步骤需要外部依赖。

解法是把分词抽成接口：

```
domain/retrieval/Tokenizer        ← 接口：文本 → 词元列表
domain/retrieval/Bm25Scorer       ← 纯算法：只接收"已经分好词的"语料
infra/tokenizer/SimpleTokenizer   ← 实现
```

`Bm25Scorer` 自己绝不调分词器。这样 BM25 的数学逻辑在 domain 里保持纯粹，
"用什么分词器"变成一个可替换的外部决策。

完整的权衡过程写在 [ADR-004](../adr/004-bm25-and-tokenizer-decoupling.md)，
包括三个被否掉的方案。

## 这套做法有什么代价

诚实地说，有三处成本：

1. **多写接口和实现两层。** 加一个召回方式要动两三个文件，
   而不是一个。好处是核心逻辑的测试不会因此变脆。

2. **有时要绕一下。** 比如 `RetrieverFactory` 这个接口存在的唯一理由，
   就是让 application 层能"造检索器"而不必知道怎么造。
   如果不在乎分层，完全可以不要它。

3. **需要在两个地方同时加代码。** 比如加一种召回方式，
   既要改 `RetrieverConfig.Kind` 枚举，也要改
   `CompositeRetrieverFactory` 的 switch。

**这些成本换来的东西**：核心算法可以在任何环境下被验证、
换实现不用改核心、约束由测试守住而不是靠人自觉。

如果这个项目只是一个一次性脚本，这些成本不值得。
但它要长期维护、要给别人用、要让结论可信——那就值得。
