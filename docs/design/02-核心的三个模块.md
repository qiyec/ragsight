# 核心的三个模块

`ragsight-domain` 里面按业务概念分了三块。这篇讲每块管什么，
以及**为什么它们故意用不同的对象表示同一份数据**。

---

## 三块

```
domain/
├── knowledge/     文档和切分        —— 一份文档是怎么变成片段的
├── retrieval/     召回、融合、打分   —— 一个问题是怎么找到片段的
└── evaluation/    指标              —— 找得准不准
```

三块对应 RAG 的三件事：**把知识存进去**、**把相关内容找出来**、**判断找得准不准**。

---

## 每块的内容

### knowledge：文档与切分

| 类 | 是什么 |
|---|---|
| `Document` | 一篇文档。承载"把正文切成片段"这件事 |
| `DocumentId` / `ChunkId` | 标识。`ChunkId` 形如 `billing.md#3` |
| `Chunk` | 一个片段，检索的最小单位 |
| `ChunkingStrategy` | 切分接口 + 两种实现（固定窗口、递归字符） |
| `DocumentReader` | 读文档的接口（实现是"读目录"） |

### retrieval：召回与排序

| 类 | 是什么 |
|---|---|
| `Retriever` | 召回接口：给问题，返回候选 |
| `EmbeddingModel` / `VectorIndex` | 向量化和存向量，两个接口 |
| `Tokenizer` | 分词接口 |
| `ScoredChunk` | 带分数和排名的片段 |
| `RetrievalSource` | 这个结果从哪条路来的（向量/关键词/融合/重排） |
| `Bm25Scorer` | BM25 打分（纯算法） |
| `ReciprocalRankFusion` | 多路融合（纯算法） |
| `Reranker` / `RerankerScorer` | 重排的接口和打分 |
| `LexicalOverlapScorer` | 字面重合打分（纯算法） |

### evaluation：指标

| 类 | 是什么 |
|---|---|
| `GoldenCase` | 一个标注用例：问题 + 期望片段 + 参考答案 |
| `EvaluationSet` | 一组用例。把关"用例 id 不能重复" |
| `RetrievedEvidence` | 实际召回结果，**只有标识和排名，没有分数** |
| `Metric` | 指标接口 |
| `RecallAtK` / `MRR` / `NDCG` | 三个指标的实现 |

---

## 关键设计：三个模块各说各的话

这是整个 domain 最值得讲的一点。

同一份数据，在三个模块里是**三个不同的对象**：

```
一篇文档        →  Document    （knowledge）
  ↓ 切分
一个片段        →  Chunk       （knowledge）
  ↓ 召回
带分数的候选    →  ScoredChunk （retrieval）
  ↓ 评估
只有排名        →  RetrievedEvidence （evaluation）
```

看起来像重复。为什么不从头到尾用一个对象？

### 理由：防止"顺手读分数"

假设全程用一个 `Chunk` 对象，上面挂着 `score` 字段。会出什么事？

评估指标在算 `Recall@k` 的时候，需要知道"答案有没有进前 k"。
排序的时候，手边正好有 `score`。于是很自然地会写：

```java
// 想按相关性排序，顺手用了分数
chunks.sort(comparingDouble(Chunk::getScore).reversed());
```

问题是：**不同召回器的分数根本不可比。**

| 召回方式 | 分数是什么 | 范围 |
|---|---|---|
| 向量召回 | 余弦相似度 | -1 ~ 1 |
| BM25 | 词频加权 | 0 到无上界 |
| RRF 融合 | Σ 1/(k+rank) | 大约 0 ~ 0.03 |

把 BM25 的 12.7 和余弦的 0.83 放在一起排序，结果是毫无意义的。
而且这种错误**不会报错**，只会让指标悄悄变错。

### 解法：从结构上让它做不到

`RetrievedEvidence` 里**只有片段标识和排名**，没有分数：

```java
public record RetrievedEvidence(List<Hit> hits) {
    public record Hit(ChunkId chunkId, int rank) { }
}
```

想读分数？没有那个字段。想排序？只能按排名。

这不是靠注释提醒"请不要用分数排序"，是**让错误根本写不出来**。

这比写文档有效得多——注释会被忽略，编译错误不会。

### 顺带的好处

`MRR` 和 `NDCG` 的实现也因此变简单了，因为它们只需要排名：

```java
// MRR 就是"第一个命中的排名取倒数"
int bestRank = expected.stream()
        .mapToInt(topK::rankOf)
        .filter(r -> r > 0).min().orElse(-1);
return bestRank > 0 ? 1.0 / bestRank : 0.0;
```

### 这个做法的名字

在 DDD 里这叫"限界上下文"——每个上下文有自己的通用语言，
同一个概念在不同上下文里可以（也应该）有不同的模型。

这里三块的"通用语言"确实是不同的：

- knowledge 关心"它是什么"
- retrieval 关心"它有多相关、从哪来的"
- evaluation 关心"它排第几"

用同一个对象硬凑，反而会模糊这个区别。

> 如果你在面试里被问到"DDD 的限界上下文有什么用"，
> 这个例子可以讲：**它不是为了让代码好看，是为了让某类错误写不出来。**

## 一个具体例子：`ChunkId` 为什么用"文档#序号"

```java
public record ChunkId(DocumentId documentId, int ordinal) {
    @Override
    public String toString() {
        return documentId.value() + "#" + ordinal;   // 如 billing.md#3
    }
}
```

用复合标识而不是随机 UUID，理由是**报告要能读**：

```
| 用例          | vector |
|---------------|--------|
| q-e4021       | 3      |
```

如果这里是 UUID，你没法一眼看出"3 是哪个片段"。
换成 `billing-error.md#3` 就能直接定位到文件和位置。

诊断工具的产出是给人看的，标识的可读性是功能的一部分。

## 三块之间怎么通信

**knowledge → retrieval**：`Chunk` 被包进 `ScoredChunk`。

**retrieval → evaluation**：`ScoredChunk` 被"脱去分数"变成 `RetrievedEvidence`。

**没有反向依赖。** evaluation 不知道 retrieval 内部怎么工作，
retrieval 也不知道 evaluation 要用它做什么。

组装这三块的地方是 `application` 层的 `DiagnosisEngine`。
它是唯一知道"先切分、再召回、最后算指标"这个顺序的地方。
