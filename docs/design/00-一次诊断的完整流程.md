# 一次诊断的完整流程

这篇从"敲下命令"讲到"看到报告"，把中间经过的每一步和涉及的类串起来。
看完应该能知道：想改某个效果，该动哪一层。

---

## 命令长这样

```bash
java -jar ragsight-cli.jar diagnose --corpus examples/corpus --eval examples/eval.txt
```

---

## 整体流程图

```
  用户敲命令
      │
      ▼
┌─────────────────────────────────────────────────────────────┐
│ DiagnoseCommand                （cli 层）                     │
│  1. 读参数、校验参数                                          │
│  2. 读文档          → DirectoryDocumentReader                │
│  3. 读测试集        → EvalFileReader                          │
│  4. 决定要对比哪些方案 → ExperimentPlan / RetrieverConfig      │
│  5. 装配向量模型     → DeterministicHash 或 OpenAiCompatible   │
└──────────────────────────┬──────────────────────────────────┘
                           │ DiagnosisRequest
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ DiagnosisEngine                （application 层）            │
│                                                              │
│  对每一个"切分方案"：                                         │
│    ① plan.chunk(文档)  → 切出一批片段                         │
│    ② 把测试集的期望文字落到这批片段上（重新找一遍）             │
│    ③ 按这批片段造检索器工厂                                   │
│                                                              │
│    对每一个"召回方案"：                                       │
│      ④ factory.create(方案, topK, 要不要重排)                │
│      ⑤ 对每个用例跑一次召回 → RetrievedEvidence               │
│      ⑥ 算指标 Recall@k / MRR / nDCG                          │
│                                                              │
│  ⑦ 用固定规则从指标推导结论                                    │
└──────────────────────────┬──────────────────────────────────┘
                           │ DiagnosisReport
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ ReportRenderer                 （cli 层）                    │
│  把报告渲染成 Markdown                                        │
└─────────────────────────────────────────────────────────────┘
```

## 逐步细看

### 第 1 步：读文档

`DiagnoseCommand` → `DirectoryDocumentReader`

读目录下所有 `.md` / `.markdown` / `.txt`，每个文件变成一个 `Document`。

两个细节值得注意：

- **文档 id 用相对路径**（如 `guide/billing.md`），不是序号。这样报告里才能指出
  "是哪个文件的哪一段出了问题"。用序号定位不到文件，等于白诊断。
- **分隔符统一成 `/`**。否则同一份文档在 Windows 上是 `guide\billing.md`、
  在 Linux 上是 `guide/billing.md`，测试集里写的期望文字就跨平台对不上了。

### 第 2 步：读测试集

`EvalFileReader` → `GoldenCaseSetSpec`

测试集文件里写的是"期望召回的**文字**"，不是片段编号。得到的是一个
`GoldenCaseSetSpec`——**还没和具体片段对应上**的描述。

为什么不直接用片段编号：编号取决于切分参数（`billing.md#3` 里那个 3），
一调切分就指向不存在的片段，指标全变 0，而你多半会以为是检索坏了。

### 第 3 步：决定对比哪些方案

两个维度分开建模：

| 维度 | 类型 | 决定什么 |
|---|---|---|
| 切分 | `ExperimentPlan` | 用哪种切分策略、切分参数、取前几条、要不要重排 |
| 召回 | `RetrieverConfig` | 用向量召回、关键词召回，还是两者融合 |

两者的组合由 `ExperimentId`（切分 id + 召回 id）标识。

**基准永远是第一个切分 × 第一个召回。** 这是刻意的约定：
调用方应该把"现在线上用的那套"放第一位，这样报告里所有差值都是相对现状算的。

### 第 4 步：装配向量模型

- 不指定 `--embedding-model`：用 `DeterministicHashEmbedding`（离线哈希）。
  不联网、不用 Key、结果可复现，但**只认字面重合**。
- 指定了：用 `OpenAiCompatibleEmbedding`。连上时会探测维度，失败立刻报错。

### 第 5 步：诊断引擎主循环

`DiagnosisEngine.diagnose()` 是整个过程的核心。它的嵌套循环：

```
for 切分方案:                          ← 每个方案各切一遍
    片段 = plan.chunk(文档)
    测试集 = caseSpec.materialize(片段)   ← 期望文字重新落到这批片段上
    工厂 = factoryProvider(片段)          ← 按这批片段造工厂

    for 召回方案:                       ← 组合出 N×M 次实验
        检索器 = 工厂.create(召回方案, topK, 要不要重排)
        for 测试用例:
            结果 = 检索器.retrieve(问题, topK)
        算指标
```

**三个容易踩的点**（都是实际踩过或差点踩的）：

1. **切分必须在这里做，不能在调用方做。**
   如果语料是"切好之后"传进来的，一个请求就只能有一种切分结果，
   那"该不该改切分"这个问题就永远答不了。

2. **测试集要在每个切分下重新对应一遍。**
   不同切分切出来的片段不一样，复用上一轮的对应关系会指向错的片段。

3. **每个切分方案要重新造检索器。**
   不同切分切出的片段不同，检索器必须按对应的片段重建。
   共用一个会让后一个覆盖前一个的索引，实验结果互相污染——
   这种错误在小语料上不容易发现，但会让整份报告失去意义。

### 第 6 步：跑召回

`RetrieverFactory.create()` 返回一个 `Retriever`，由它具体执行召回。

四种可能拿到的东西：

| 召回方案 | 要不要重排 | 实际得到的 |
|---|---|---|
| 仅向量 | 否 | `VectorRetriever` |
| 仅关键词 | 否 | `Bm25Retriever` |
| 融合 | 否 | `HybridRetriever`（包着上面两个） |
| 任意 | 是 | `RerankedRetriever`（包着上面任意一个） |

这是**装饰器**：重排不改变召回的实现，只是包一层。

### 第 7 步：算指标

测试集里每个用例的召回结果先转成 `RetrievedEvidence`——
**只保留"片段标识 + 排名"，丢掉分数**。

这一步是有意的：不同召回器的分数根本不可比（余弦相似度在 -1~1，
BM25 是无上界的正数）。只留排名，就从结构上杜绝了"拿分数算指标"这类错误。

然后三个指标各算一遍：

- `RecallAtK` —— 有没有捞到
- `MRR` —— 第一个对的排第几
- `NDCG` —— 整体排序质量

指标接口是 `Metric`，`scoreAll()` 会跳过返回 `NaN` 的用例。
负样本（"本来就该答不出来"的问题）在排序类指标里没有定义，
所以返回 `NaN` 让它不参与平均。

### 第 8 步：推导结论

`deriveFindings()` 用固定规则从指标推出结论。**不调大模型。**

规则一共四组：

| 规则 | 看什么 | 说出什么 |
|---|---|---|
| 召回够不够 | `Recall@k` | "召回不够，先别管排序" 或 "召回够用，瓶颈在排序" |
| 排序够不够 | `MRR` 低但 `Recall` 高 | "这是排序问题，该试重排" |
| 切分有没有影响 | 各切分方案的指标差 | "切分有影响" 或 "别在切分上花时间了" |
| 换召回有没有收益 | 各召回方案的指标差 | "值得换" 或 "不值得增加复杂度" |

**为什么不用大模型写结论**：同一份输入必须得到同一份报告。
用户要拿这份报告去改生产配置，结论不稳定的话他不敢用。

### 第 9 步：渲染

`ReportRenderer` 把 `DiagnosisReport` 转成 Markdown。

它**只负责展示，不做判断**。所有结论都是引擎用固定规则推出来的，
渲染阶段不再加任何新逻辑——否则同一份数据可能显示出两种结论。

## 数据在层之间怎么流动

```
Document  ──切分──▶  Chunk  ──召回──▶  ScoredChunk  ──脱去分数──▶  RetrievedEvidence
 （文档模块）        （文档模块）       （召回模块）                  （评估模块）
```

注意这四步用的**不是同一个对象**，是四个：

| 对象 | 关心什么 | 在哪个模块 |
|---|---|---|
| `Document` | 这篇文档是什么 | knowledge |
| `Chunk` | 这一片是什么 | knowledge |
| `ScoredChunk` | 它排第几、从哪条路召回的 | retrieval |
| `RetrievedEvidence` | 它排第几（不要分数） | evaluation |

看起来有点像重复。这是故意的，理由见
[02-核心的三个模块](02-核心的三个模块.md)——简单说，
如果全程用一个万能对象，评估指标就会顺手去读那个不可比的分数。

## 想改某个效果，该动哪一层

| 你想改 | 动哪里 |
|---|---|
| 怎么切分 | `domain/knowledge/chunking/` 加实现 |
| 怎么召回 | `domain/retrieval/Retriever` 加实现 + `infra/retriever/` |
| 怎么打分/融合 | `domain/retrieval/`（纯算法，可手算验证） |
| 怎么算指标 | `domain/evaluation/` 加 `Metric` 实现 |
| 用什么向量模型 | `infra/embedding/` |
| 存哪、怎么存向量 | `infra/index/` |
| 读什么格式的文档 | `infra/reader/` |
| 结论怎么写 | `application/DiagnosisEngine.deriveFindings()` |
| 报告长什么样 | `cli/report/ReportRenderer` |
| 加命令行参数 | `cli/command/DiagnoseCommand` |

具体的改动步骤见 [04-二次开发指南](04-二次开发指南.md)。
