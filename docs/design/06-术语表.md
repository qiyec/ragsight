# 术语表

这个项目里的词，用大白话解释一遍。每个都尽量说清"为什么要关心它"。

按主题分组，不是按拼音。

---

## 检索是怎么做的

### RAG（检索增强生成）

先拿问题去文档里找出相关内容，再把"问题 + 找出来的内容"一起给大模型，
让它基于这些内容回答。

**为什么要这么做**：大模型不知道你的私有文档，而且它可能编。
给它真实材料，答案就靠谱得多。

### 切分（Chunking）

把长文档切成一段一段。因为模型的上下文有长度限制，
而且一整篇文档塞进去，真正相关的那几句会被淹没。

**为什么要关心**：切分是 RAG 最容易出问题、也最容易被瞎调的一步。
切太碎，一个片段说不完整一件事；切太大，一个片段里混进太多无关内容。

### 片段（Chunk）

切分之后的一小段。检索的最小单位——你要么整个召回它，要么不召回。

### 向量（Embedding）

把一段文字变成一串数字（比如 1024 个数）。意思是把它放到一个
高维空间里的某个位置。**意思相近的文字，位置也接近。**

**为什么要关心**：它是"语义检索"能工作的基础。
但它不是万能的——见下面的"字面重合"。

### 召回（Retrieval）

拿问题去找最相关的几个片段。常见的有三种做法：

| 做法 | 擅长 | 不擅长 |
|---|---|---|
| **向量召回** | 意思相近但用词不同（"账单" ↔ "费用结算"） | 精确的编号、术语（"E4021" 容易被常见词淹没） |
| **关键词召回** | 精确的术语、编号、专有名词 | 同义改写（问"账单什么时候出"，文档写"账单生成时间"，一个词都对不上） |
| **混合** | 两者互补 | 多一层复杂度，而且不一定有收益 |

**为什么要关心**：这三者的差别是诊断报告最常见的结论之一。
本项目实测过：在演示语料上"仅关键词召回"比"仅向量召回"的 MRR 高 0.135。

### topK

召回时取最相关的前几条。

**为什么要关心**：取太少可能漏掉正确答案；取太多会把上下文塞满无关内容，
反而让模型分心。这个数值得用数据定，不该拍脑袋。

### 重排（Rerank）

先召回来一大批候选（比如 20 条），再用一个更精细的模型重新排一遍，
取前 5 条。

**为什么要关心**：它能明显提升排序质量，但有代价——慢，而且贵
（要对每个"问题+片段"组合单独算一次）。

⚠️ **重排救不回没召回到的东西。** 如果候选里根本没有正确答案，
重排只能把错的排得更整齐。所以诊断顺序永远是**先看召回率，再看排序质量**。

## 怎么判断做得好不好

### 测试集 / 标注用例

一批"问题 + 正确答案在哪个片段"的数据。用来量效果。

**为什么要关心**：没有它就只能靠感觉调参数。而"感觉"在不同人之间、
不同时间之间都不一致。

### 负样本

"知识库里本来就没有答案"的问题。比如问一个文档里从没提过的功能。

**为什么要关心**：**没有负样本，一个"永远返回最相似内容"的检索器也能拿高分。**
这是测试集必须包含负样本的唯一理由，也是最容易被忽略的一点。

本项目在没有负样本时会在报告里主动提醒。

### Recall@k（召回率）

期望的片段里，有多少比例出现在前 k 条结果里。

**为什么要关心**：它是**上限**。如果 Recall@5 = 0.6，意味着四成的问题
连候选都没有——这种情况下把重排做得再好、上下文拼得再漂亮，也答不对。

诊断顺序：先看 Recall，再看排序。

### MRR（平均倒数排名）

第一个正确答案排在第几，取倒数，再对所有问题求平均。
排第 1 得 1.0、第 2 得 0.5、第 4 得 0.25。

**为什么要关心**：它衡量"用户多快能看到正确答案"。
Recall 高但 MRR 低，说明内容都找到了，但排得不好——这是**排序问题**，
解决办法是加重排，不是继续调切分。

### nDCG

考虑**整个排序列表**的质量，位置越靠后折损越大。

**为什么要关心**：MRR 只看第一个正确答案的位置，假设"找到一个就够了"。
但上下文能放好几个片段，用户可能期望多个答案点（"列出所有相关条款"）。
这时候第二个、第三个相关结果排得怎么样也重要，而 MRR 对此完全不敏感。

一句话分工：**Recall 看有没有捞到，MRR 看第一个对的排得靠不靠前，
nDCG 看整体排得好不好。**

### 手算验证

拿具体的数字，按公式在纸上推一遍，看实现算出来的是不是一样。

**为什么要关心**：拿实现自己的输出当预期值，测试只能证明"代码没改"，
证明不了"算得对"。本项目所有指标和算法都做了手算验证，
推导过程写在测试的注释里。

## 本项目用到的具体方法

### BM25

关键词召回最常用的打分公式。核心想法是：

- 一个词在**越少**文档里出现，它越有区分度（"的"到处都是，没用；
  "E4021"只在一条里出现，很有用）
- 一个词在**同一篇**里出现越多，这篇越相关，但收益递减
  （出现 10 次不比出现 5 次重要一倍）
- **长文档要压一压**（它因为词多，偶然命中的机会更大）

两个参数：`k1` 控制"收益递减有多快"，`b` 控制"长文档压多少"。

### RRF（倒数排名融合）

把多路召回的结果合并成一个。每路按 `1/(k + 排名)` 给分，加起来。

**为什么用排名而不是分数**：不同召回器的分数根本不可比——
余弦相似度在 -1~1，BM25 是 0 到无上界。硬要加权求和就得先归一化，
而归一化方式本身又是个调参黑洞。**RRF 只用排名，天然免了这件事。**

代价是丢掉了"第 1 名遥遥领先"这种信息。这是明确的取舍。

### 字面重合（本项目用来当重排基线）

算"问题里的词有多少出现在候选片段里"。

**它存在的意义不是效果好，是当基线**：想说"加重排有没有用"，
得先有个能跑的；想证明"真模型比简单方法好"，也得先有个简单方法作对照。

它的能力边界很明确：只认字面。问"账单什么时候出"、
文档写"账单生成时间"，它一个词都对不上。真模型能理解这种关联，它不能。

### 离线哈希向量化（默认用的）

把文字按字符散列成一串数字。**不联网、不用 Key、结果可复现。**

**能力边界**：它只认字面重合，**没有语义泛化能力**。
本项目实测过：

| 文本对 | 余弦相似度 | 说明 |
|---|---|---|
| 计费规则 / 收费规则 | 0.7500 | 共享「费规则」3 个字 |
| **计费 / 收费** | **0.5000** | 意思一样但一个字都不共享 |
| 计费规则 / 天气晴朗 | 0.0000 | 零重合精确为 0 |

中间那行说明了一切：两个意思完全相同的词，得分和"部分相关"一个量级。

**所以它的绝对分数没有参考价值**，只能用来验证流程跑得通。
想要有意义的数字，得接真实模型（`--embedding-model`）。

## 工程上的词

### 可复现

同样的输入，跑两次得到同样的结果。

**为什么要关心**：用户要**拿这份报告去改生产配置**。
如果结论本身不稳定，他不敢用，那这个工具就没有意义。

所以本项目规定：

- 排序遇到同分时，按一个固定的次级键排（不能"保持原顺序"——
  原来的顺序可能本身就不稳定）
- 不许用随机数
- 不许调大模型来生成结论

### 架构测试 / 门禁

用测试代码检查架构约束，违反了构建就失败。

**为什么要关心**：光写"不许依赖"没用，时间一长总有人顺手 import 一下。
把规矩变成测试，就不靠人自觉了。

本项目有 5 条规则，还专门写了测试确认它们**真的会拦人**——
因为规则写错包名、或者包被改名之后会静默失效：
构建照样通过，但实际什么都没检查。这种"以为有门禁、其实没有"
比没有门禁更危险。

### 接口 / 实现分离

需要外部能力的地方（调模型、读文件、存向量）定义一个接口，
接口放在核心模块，实现放在外层。

**为什么要关心**：换实现不用改核心代码。而且核心逻辑因此能在
没有网络、没有数据库、没有 API Key 的环境下被完整测试。

### 依赖注入

需要什么，由外面传进来，不在里面自己 new。

```java
// 不好：写死了
Retriever retriever = new VectorRetriever();

// 好：由外面给
public DiagnosisEngine(RetrieverFactory factory) { ... }
```

**为什么要关心**：测试的时候可以传一个假的进去，
不用真的去连数据库或调接口。本项目的诊断引擎测试就是这么做的。

### 装饰器

给一个对象加一层能力，但不改它本身。

本项目里"重排"就是一个装饰器：它包住任意一种召回器，
先多要几倍候选，重排后返回前 K 条。加一种召回方式不用再写一个
"带重排的版本"。

## 本项目特有的词

### 实验（Experiment）

一次"用某套条件跑完整测试集"。条件包括：用哪种切分、取前几条、
要不要重排，以及用哪种召回方式。

### 实验条件 / 方案（Plan）

"用哪种切分、取前几条、要不要重排"。**不含召回方式**——
那是另一个维度。两个维度组合起来才是"一次实验"。

### 可归因

指标的变化能对应到某个具体改动上。

**为什么要关心**：如果一次实验同时改了切分和重排，
指标变了你也不知道是哪个造成的。报告在这种情况下会明确说
"没法归因"，而不是瞎猜一个。

反过来，报告会尽量把能拆开的拆开说：
重排的效果用"同一刀切分、一加一不加"的配对方案比；
切分的效果用"都不加重排"的方案之间比。
