# 设计模式清单

这篇列出项目里**实际用到**的模式。每个都说清：解决什么问题、
不用会怎样、在哪个文件。**没用的模式不会写进来**——凑数没意义。

---

## 速查表

| 模式 | 用在哪 | 解决的问题 |
|---|---|---|
| 策略 | `ChunkingStrategy`、`Retriever`、`Reranker` | 同一件事有多种做法，要能换 |
| 简单工厂 | `CompositeRetrieverFactory` | 按配置造出对应的实现 |
| 配置表（枚举） | `RetrieverConfig.Kind` | 可选方案是有限且固定的 |
| 值对象 | 几乎所有的 `record` | 数据不可变、构造时就校验 |
| 仓储 | `DocumentReader` | 数据从哪来和怎么用分开 |
| 聚合一致性 | `EvaluationSet`、`DiagnosisReport` | 集合层面的约束要有人把关 |
| 适配器 | `OpenAiCompatibleEmbedding` | 外部接口格式不归我们定 |
| 装饰器 | `RerankedRetriever` | 加一层能力而不改原来的实现 |
| 组合 | `HybridRetriever` | 多个同类对象当成一个用 |
| 外观 | `DiagnosisEngine` | 把一串步骤包成一个调用 |
| 默认方法 | 各接口的 `name()`、`scoreAll()` | 给实现一个合理的默认行为 |

## 1. 策略（Strategy）

**用在哪**：`ChunkingStrategy`、`Retriever`、`Reranker`、`RerankerScorer`、
`Metric`、`EmbeddingModel`、`VectorIndex`、`Tokenizer`、`DocumentReader`

**解决什么问题**：同一件事有几种做法，而且做法会被替换或对比。

**不用会怎样**：只能写一个类，里面用 `if-else` 分支选做法。
每加一种做法就要改那个类，改的时候容易碰坏别的分支。

最能说明问题的是切分：

```java
// 不用策略的话，会写成这样
public List<Chunk> chunk(String text, String type, int size, int overlap) {
    if ("fixed".equals(type)) {
        ...
    } else if ("recursive".equals(type)) {
        ...
    } else if ("semantic".equals(type)) {   // 新加的
        ...
    }
    // 这个方法会越来越长，参数会越来越多
}
```

用策略之后，加一种切分就是**加一个新类**，不改任何已有代码：

```java
public interface ChunkingStrategy {
    String name();
    String describe();
    List<Chunk> chunk(Document document);
}
```

**为什么接口里有 `describe()`**：诊断报告要区分"同一个策略配不同参数"
（比如 512/128 和 256/64 是两个不同的实验）。光有 `name()`
分不出来，所以要求每个实现自己说明参数。

## 2. 简单工厂（Simple Factory）

**用在哪**：`CompositeRetrieverFactory`

**解决什么问题**：调用方知道"我要哪种"，但不想知道"怎么造"。

**不用会怎样**：`DiagnosisEngine` 里会出现这样的代码：

```java
// 如果引擎自己 new，那它就得认识所有实现
Retriever retriever = switch (config.kind()) {
    case VECTOR_ONLY -> new VectorRetriever(new DashScopeEmbedding(...), new PgVectorIndex(...));
    case KEYWORD_ONLY -> new Bm25Retriever(new SimpleTokenizer(), corpus);
    ...
};
```

问题是 `DiagnosisEngine` 在 application 层，而
`VectorRetriever`、`DashScopeEmbedding` 这些都在 infrastructure 层。
**依赖方向就反了**，架构测试会直接失败。

所以把"造"这件事抽成 `RetrieverFactory` 接口（在 application 层），
实现放 infrastructure：

```
application/RetrieverFactory          ← 接口：按配置造检索器
infra/CompositeRetrieverFactory       ← 实现：真的去 new
```

这样引擎只管"要一个检索器"，不管它是怎么来的。

**注意这是"简单工厂"不是"工厂方法"**：没有继承体系，
一个类里一个 `switch` 就够了。工厂方法那套（抽象工厂类 + 子类工厂）
在这个规模下是过度设计。

---

## 3. 配置表（用枚举代替分支）

**用在哪**：`RetrieverConfig.Kind`

**解决什么问题**：可选方案是有限、固定的几种，而且每种都要有
展示名、要能在报告里出现。

**不用会怎样**：用字符串常量的话，拼错了编译期发现不了：

```java
// 字符串方案：拼错了要到运行时才知道
new RetrieverConfig("vectorr", "仅向量召回");   // 编译能过，跑起来才出错
```

用枚举的话，可选值就那三个，IDE 能补全，拼错编译不过：

```java
public enum Kind {
    VECTOR_ONLY("仅向量召回"),
    KEYWORD_ONLY("仅关键词召回"),
    HYBRID_RRF("向量+关键词 融合");

    private final String label;   // 报告里显示的名字
    public String label() { return label; }
}
```

**顺带把中文标签挂在枚举上**，而不是散在渲染代码里的 `switch`。
加一种方案时，标签跟着一起加，不会漏。

## 4. 值对象（Value Object）

**用在哪**：`ChunkId`、`DocumentId`、`Chunk`、`Document`、
`ScoredChunk`、`GoldenCase`、`RetrievedEvidence`、`ExperimentId`……

**解决什么问题**：有些数据是不可变的，而且**构造时就必须合法**。

**不用会怎样**：用可变对象 + 到处传的话，
会出现"不知道谁改了它"和"里面是脏数据"两类问题。

做法是 `record` + 紧凑构造器校验：

```java
public record ChunkId(DocumentId documentId, int ordinal) {
    public ChunkId {
        if (documentId == null) {
            throw new IllegalArgumentException("documentId 不能为空");
        }
        if (ordinal < 0) {
            throw new IllegalArgumentException("ordinal 不能为负数：" + ordinal);
        }
    }
}
```

**关键在"构造时就校验"**：不合法的对象根本创建不出来，
所以永远不用在别处写 `if (chunk.getId() == null)`。
把检查放在边界上，后面的代码就可以假设数据是干净的。

**为什么不用 Lombok**：JDK 17 的 `record` 已经把值对象这件事做完了。
引一个编译期字节码增强的库，收益不大，代价是构建和 IDE 的兼容性问题。

---

## 5. 仓储（Repository）

**用在哪**：`DocumentReader`

**解决什么问题**：把"数据从哪来"和"数据怎么用"分开。

**不用会怎样**：如果 `DiagnosisEngine` 直接写
`Files.walk(dir).filter(...).map(Files::readString)`，
那它就和"本地文件系统"绑死了。想从压缩包、对象存储、
或者测试里直接给一批文档，都得改它。

抽成接口之后：

```java
public interface DocumentReader {
    List<Document> readAll();
    String describe();
}
```

诊断流程只认这个接口。测试里可以给一个内存实现（`DiagnosisFixtures` 就是），
生产里给 `DirectoryDocumentReader`，将来加"读 S3"也不用动流程。

**注意 `describe()` 也在接口里**：报告里要说清"这次读的是哪批文档"。
把来源描述和读取能力放一起，比在别处猜要好。

> 这个模式在 DDD 里叫 Repository，在这个项目里它很简单——
> 就是一个"读进来"的接口，不涉及增删改和事务。
> 不必为了套模式而把它做复杂。

---

## 6. 聚合一致性（Aggregate）

**用在哪**：`EvaluationSet`、`DiagnosisReport`

**解决什么问题**：有些约束**只有在集合层面才能检查**，
单个元素看不到。

**不用会怎样**：以 `EvaluationSet` 为例，它把关的是"用例 id 不能重复"。

单个 `GoldenCase` 没法知道自己和别的用例重名了。如果不在集合层校验，
重复 id 会一路流到报告里：

```
| 用例      | vector |
|----------|--------|
| q-001    | 3      |
| q-001    | —      |     ← 哪个 q-001？
```

报告里说"q-001 没召回到"，但你不知道是哪个 q-001。
**归因直接失真**，而且不会报错。

所以 `EvaluationSet` 构造时检查：

```java
public record EvaluationSet(String name, List<GoldenCase> cases) {
    public EvaluationSet {
        ...
        // 找出重复的 id 并报错
        if (!duplicates.isEmpty()) {
            throw new IllegalArgumentException(
                    "评测集内用例 id 重复，会导致归因失真：" + duplicates);
        }
    }
}
```

`DiagnosisReport` 把关的是另一件事：**基准必须真的在结果里**。
否则后面所有"相对基准的变化"都算不出来。

**这类校验放在构造器里**，是因为不满足条件的对象根本不该存在。

---

## 7. 适配器（Adapter）

**用在哪**：`OpenAiCompatibleEmbedding`

**解决什么问题**：外部接口的格式不归我们定，但我们的代码要有稳定的接口。

**不用会怎样**：如果把 HTTP 调用和 JSON 解析直接写进
诊断流程，那换一家模型供应商就要改流程代码。
而且 domain 层会被迫认识 `HttpClient`、`ObjectMapper` 这些东西——
架构测试会直接失败。

适配器做的是翻译：

```
domain 要的：            float[] embed(String text)
外部接口要的：  POST /embeddings  {"model":"...","input":["..."]}
                ← {"data":[{"index":0,"embedding":[...]}]}
```

`OpenAiCompatibleEmbedding` 实现 domain 的 `EmbeddingModel` 接口，
内部把 HTTP 和 JSON 都包起来。换供应商只改 `baseUrl` 和模型名。

**这个适配器还处理了两个外部世界的"不讲理"之处**：

1. **服务端不保证按请求顺序返回向量**，所以必须按 `index` 归位。
   不归位的话文本和向量会错位，而且**检索结果看起来完全正常**——
   那是静默的灾难。
2. **`dimensions` 参数不是所有兼容接口都支持**，所以不传。
   维度靠连上时探测一次。

这两条不是设计模式，是"和外部系统打交道时必须假设对方会不讲理"。

---

## 8. 装饰器（Decorator）

**用在哪**：`RerankedRetriever`

**解决什么问题**：要给一个对象加一层能力，但不想改它的实现，
也不想为每种组合各写一个类。

**不用会怎样**：重排是"召回之后加一步"。如果不用装饰器，
就得为每种召回方式各写一个"带重排的版本"：

```
VectorRetriever
VectorRetrieverWithRerank        ← 重复
Bm25Retriever
Bm25RetrieverWithRerank          ← 重复
HybridRetriever
HybridRetrieverWithRerank        ← 重复
```

加一种召回方式，就要多写两个类。而且重排的逻辑抄了三遍。

用装饰器之后，一个类搞定：

```java
public final class RerankedRetriever implements Retriever {
    private final Retriever delegate;    // 里面包着任意一种召回器
    private final Reranker reranker;

    @Override
    public List<ScoredChunk> retrieve(String query, int topK) {
        // 先多要一些候选给重排留腾挪空间，再重排后返回前 K 条
        List<ScoredChunk> candidates = delegate.retrieve(query, topK * 4);
        return reranker.rerank(query, candidates, topK);
    }
}
```

**"先多要几倍候选"这件事很关键**，值得单独说：
重排只能在已召回的候选里重排，救不回没召到的东西。
如果召回时就只要 5 条，重排最多在这 5 条里挪位置，几乎看不出区别——
**还会让人误以为"重排没用"**。

## 9. 组合（Composite）

**用在哪**：`HybridRetriever`

**解决什么问题**：几个"同类对象"要当成一个用。

**不用会怎样**：融合检索需要调用向量召回和关键词召回各一次，
再把结果合并。如果不做组合，这段逻辑会写死在某个地方，
以后想加第三路（比如按标题召回）就要改那个地方。

`HybridRetriever` 持有一个 `List<Retriever>`：

```java
public final class HybridRetriever implements Retriever {
    private final List<Retriever> routes;   // 几路都行

    @Override
    public List<ScoredChunk> retrieve(String query, int topK) {
        List<List<ScoredChunk>> results = new ArrayList<>();
        for (Retriever route : routes) {
            results.add(route.retrieve(query, candidatesPerRoute));
        }
        return fusion.fuse(results, topK);   // 融合算法在 domain
    }
}
```

它自己也是 `Retriever`，所以还能再被 `RerankedRetriever` 包一层。
**装饰器和组合能自由套在一起**，这是接口设计得好的直接收益。

---

## 10. 外观（Facade）

**用在哪**：`DiagnosisEngine.diagnose()`

**解决什么问题**：一次诊断涉及七八个步骤，调用方不该关心它们的顺序。

**不用会怎样**：调用方要自己写：

```java
// 如果引擎不封装，命令里就得写这些
List<Chunk> chunks = strategy.chunk(documents);
EvaluationSet evalSet = caseSpec.materialize(chunks);
RetrieverFactory factory = new CompositeRetrieverFactory(...);
for (RetrieverConfig config : configs) {
    Retriever retriever = factory.create(config, topK, false);
    for (GoldenCase c : evalSet.cases()) { ... }
    // 算指标、算差值、推结论……
}
```

这段顺序**不能乱**（测试集必须等切分完才能对应到片段上），
但让每个调用方都记住它是不现实的。

`diagnose()` 把它收成一个方法：

```java
DiagnosisReport report = new DiagnosisEngine(factoryProvider).diagnose(request);
```

CLI 只需要准备输入和渲染输出，中间的全在引擎里。

## 11. 默认方法（给实现一个合理默认）

**用在哪**：`Metric.scoreAll()`、`EmbeddingModel.embedOne()`、
各接口的 `name()`

**解决什么问题**：有些行为所有实现都一样，或者有个合理默认值，
不该逼每个实现都写一遍。

**不用会怎样**：`Tokenizer` 有 3 个实现的话，
`name()` 那段"返回类名"的代码要抄 3 遍。改的时候容易漏。

用默认方法：

```java
public interface Tokenizer {
    List<String> tokenize(String text);

    default String name() {
        return getClass().getSimpleName();   // 默认用类名，想改就覆盖
    }
}
```

**`Metric.scoreAll()` 是最有价值的一个**。它不只是省代码，
而是把一条规则固定下来：

```java
default double scoreAll(EvaluationSet evalSet, List<RetrievedEvidence> evidences) {
    double sum = 0;
    int counted = 0;
    for (int i = 0; i < evalSet.size(); i++) {
        double s = score(evalSet.cases().get(i), evidences.get(i));
        if (!Double.isNaN(s)) {      // 跳过负样本
            sum += s;
            counted++;
        }
    }
    return counted == 0 ? 0.0 : sum / counted;
}
```

"负样本在排序类指标里不参与平均"这条规则写在默认实现里，
所有指标自动遵守。如果让每个 `Metric` 自己实现，
迟早有一个会忘掉这个处理，然后 `MRR` 和 `nDCG` 的口径就不一致了。

> 这个方法在 design pattern 书里有个名字叫"模板方法"，
> 不过这里没有继承体系，就是接口的默认实现。
> 名字不重要，重要的是**规则只写一遍**。

## 刻意没用的模式

列出来是因为"不用"本身也是设计决定，面试里常被追问。

| 模式 | 为什么不用 |
|---|---|
| **单例** | 这个项目没有需要全局唯一的状态。需要共享的东西（配置、工厂）由调用方创建和传递，用依赖注入比全局变量好测 |
| **观察者** | 没有"状态变化要通知多方"的需求。报告是跑完一次性生成的，不是持续订阅的 |
| **责任链** | 一开始我设想过把检索做成"管道 + 一串 Stage"（`RetrievalStage`），后来没做。因为当前只有"召回 → 重排"两步，用装饰器足够了。为两步建一套链式框架是过度设计 |
| **抽象工厂** | 只有一个产品族（检索器），没有"换一整套相关实现"的需求。简单工厂够用 |
| **建造者** | 除了 `HttpClient.newBuilder()`（JDK 自带的），没有参数特别多的构造。`record` 的构造器已经够清楚 |
| **Lombok** | JDK 17 的 `record` 覆盖了主要场景。引编译期字节码增强的库，收益小、代价大（IDE 和构建工具的兼容性） |

**判断标准**：每用一个模式，都要能回答"不用它会怎样"。
回答不出来，就是凑数。

## 这些模式之间的关系

它们不是孤立的，串起来是这样：

```
策略    ──  每种做法一个类（ChunkingStrategy / Retriever / Metric）
  │
  ├─ 简单工厂  ──  按配置把对应的那个类造出来
  │
  ├─ 装饰器    ──  在某个做法外面加一层（重排）
  │         │
  │         └─ 组合  ──  几个同类做法当成一个（多路融合）
  │
  └─ 外观    ──  把"选做法、跑、算、推结论"包成一个调用

值对象 / 仓储 / 聚合一致性  ──  横向支撑：数据干净、来源可换、约束有人管
适配器                      ──  在边界上翻译外部世界的格式
```
