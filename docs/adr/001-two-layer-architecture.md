# ADR-001：为什么分成"确定性引擎 + Agentic 诊断器"两层

- **状态**：已接受
- **日期**：2026-10-13
- **决策者**：项目发起人

---

## 背景

ragsight 要解决"RAG 效果不好，但不知道是哪个环节坏了"。

一个直觉做法是：直接做一个基于 LLM 的 Agent，把文档和问题丢给它，让它分析并给出结论。
但这会带来一个致命问题：**诊断结论不可复现**。

同一个知识库、同一个评测集，跑两次可能得到不同的瓶颈判断。而用户拿到诊断结论后要据此**改动生产配置**——如果结论本身不稳定，这个工具就没有存在价值。

同时，穷举式诊断存在**组合爆炸**：

```
6 种切分策略 × 3 种检索方式 × 2 种重排 = 36 组实验
每组实验要跑完整评测集（假设 100 个 case）
```

静态跑完所有组合，时间和调用成本都不可接受。

---

## 决策

**分成两层，职责严格分离：**

| 层 | 职责 | 技术 | 允许的依赖 |
|---|---|---|---|
| **第一层：诊断引擎** | 定义并执行单个实验，计算指标，产出可复现的度量结果 | 纯 Java | 无（零第三方运行时依赖） |
| **第二层：Agentic 诊断器** | 决定下一个实验做什么，形成假设并收敛结论 | AgentScope | 全部外部依赖 |

**第一层是唯一能产出数字的地方。第二层只能编排实验和解释结果，不能自己计算指标。**

---

## 理由

### 1. 指标计算必须确定

`Recall@k`、`MRR`、`nDCG` 是纯函数：给定检索结果和标注答案，输出唯一确定的数值。
这类计算没有任何理由引入 LLM——引入只会让它变慢、变贵、且不可信。

### 2. 可复现性是诊断工具的生命线

用户需要能验证我们的结论。如果报告说"混合检索把 Recall@5 从 0.62 提到 0.81"，
用户必须能自己重跑得到同样的数字。这要求实验执行路径完全确定。

### 3. 组合爆炸需要智能决策，而不是穷举

36 组全跑是浪费。真实场景里，瓶颈往往是**单一环节**：

- 如果是切分把答案切断了，那换检索方式怎么调都没用
- 如果召回集里根本没有正确答案，重排再强也救不回来

因此正确策略是**先定位粗粒度瓶颈，再在其上细调**——这是一个依赖前序结果的自适应搜索过程，
**事先编排不出来**。这正是 Agent 的适用场景。

### 4. 两个失败模式不能互相污染

- 如果指标计算依赖 LLM → 数字不可信（诊断错了没人知道）
- 如果实验编排是静态的 → 浪费预算且无法深入（诊断不够好）

分成两层后，两者可以**独立验证**：
- 第一层用元评测验证（构造已知缺陷的夹具，检查结论是否正确，见 `docs/adr/005`）
- 第二层用实验次数、收敛性、结论质量来评估

---

## 被否决的方案

### 方案 A：全静态穷举，不做 Agent

- ❌ 36 组实验的成本和时间不可接受
- ❌ 无法根据中间结果深入挖掘

### 方案 B：纯 LLM 诊断（一个 prompt 搞定）

- ❌ 结论不可复现
- ❌ 指标计算交给 LLM 会引入幻觉——LLM 算不对 `nDCG` 的
- ❌ 无法验证对错

### 方案 C：LLM 只做最后总结

- ⚠️ 比方案 B 好，但没解决"下一步试什么"的自适应搜索问题
- 最终选定方案的**第二层**已包含此能力，且更强

---

## 影响

### 正面

- 诊断结论**可复现、可验证、可信**
- 第一层**零依赖**，可以在没有网络、数据库、API Key 的环境下完整测试
- 分层清晰，符合六边形架构——第二层只是第一层的一个"驱动适配器"

### 负面 / 代价

- **工作量增加**：需要先建好完整的度量引擎，才能让 Agent 层有价值
  → 缓解：按 P1→P4 顺序推进，Agent 层（P5+）最后做
- **存在重复描述风险**：实验配置需要在两层都有表达
  → 缓解：实验配置对象定义在第一层，第二层通过工具接口复用，不重复定义
